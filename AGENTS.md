# AGENTS.md — Guide des agents pour Cumulus

Ce document oriente les sessions d'agents (Claude Code, Codex) qui travaillent sur ce dépôt. Il décrit le produit, le workflow et les conventions. **Lis-le en premier.**

---

## 1. Vue d'ensemble

**Cumulus** (dépôt, target et équipe Linear : « Xcode Cloud Companion ») est une app macOS qui vit dans la barre des menus. Elle surveille la consommation Xcode Cloud d'un compte App Store Connect (heures de calcul utilisées par rapport au forfait) et liste les builds récents de chaque app.

| | |
|---|---|
| Plateforme | macOS 26.0+ (`MACOSX_DEPLOYMENT_TARGET = 26.0`, XCO-151 : aucune API propre à macOS 27 n'est utilisée ; descendre sous 26 demanderait une interface sans verre) |
| Langage | Swift, SwiftUI pour les vues, AppKit pour la structure du menu |
| Target / scheme | target `xcode-cloud-companion`, scheme `Cumulus` (produit : `Cumulus.app`, module `XcodeCloudCompanion`, bundle ID `com.guik.xcode-cloud-companion`) |
| Sandbox | Activé (garder la porte du Mac App Store ouverte) |
| Dépendances | Aucune |

### Source de données : API App Store Connect

- Authentification par jeton JWT ES256, signé avec une clé API `.p8` (Issuer ID + Key ID). La clé est stockée dans le trousseau, jamais en clair.
- Chemin des données : `GET /v1/ciProducts` → `GET /v1/ciProducts/{id}/buildRuns` → `GET /v1/ciBuildRuns/{id}/actions`. Aucun endpoint ne liste d'un coup tous les builds de l'équipe.
- `ciBuildRuns` et `ciBuildActions` exposent `startedDate`, `finishedDate`, `executionProgress` (`PENDING`, `RUNNING`, `COMPLETE`) et `completionStatus` (`SUCCEEDED`, `FAILED`, `ERRORED`, `CANCELED`, `SKIPPED`). Les actions ont aussi `actionType` (`BUILD`, `ANALYZE`, `TEST`, `ARCHIVE`) et les builds `startReason`.
- ⚠️ **Aucun endpoint n'expose la consommation ni le quota Xcode Cloud** (vérifié dans la doc Apple le 09/10/2026). La consommation affichée est donc une **estimation** : la somme des durées des actions (elles tournent en parallèle sur des machines distinctes). Le forfait et le jour de réinitialisation sont saisis par l'utilisateur. Toujours présenter le chiffre comme une estimation.
- **Mesuré sur le vrai compte le 13/10/2026** (XCO-51, lecture seule) : `X-Rate-Limit` vaut `user-hour-lim:3600;user-hour-rem:…;`. `GET /v1/ciProducts` **ne pagine pas** : `limit` tronque la liste sans `links.next`, et `meta.paging.total` vaut alors le nombre rendu, pas le vrai total ; l'app demande 200, le maximum. Les listes de builds paginent : `links.next` reprend le chemin et la requête d'origine avec un `cursor` (264 caractères), que `meta.paging.nextCursor` répète. `sourceCommit` est rempli aussi hors pull request. Le `downloadUrl` d'un artefact pointe sur `cvws.icloud-content.com`, vaut environ 15 minutes (paramètre `e`, une date Unix) et se télécharge sans `Authorization` ; le jeton de l'API ne lui est jamais envoyé.
- Un build `COMPLETE` ne change plus : il se met en cache et ne se redemande pas. Seuls les builds en cours ou récents se rafraîchissent, pour ménager la limite de requêtes de l'API.

### Interface : un vrai menu natif

Le modèle est CodexBar : un `NSStatusItem` + `NSMenu`, dont certaines lignes sont des vues SwiftUI hébergées (barres de progression, chiffres, histogramme). Le reste, ce sont des `NSMenuItem` standards (sous-menus, surlignage, navigation clavier). Ne pas remplacer par un popover ni par `MenuBarExtra(.window)`.

### Architecture

**Cycle de vie AppKit**, pas d'`App` SwiftUI : `AppDelegate` porte `@main` et lance `NSApplication`. Depuis macOS 14, la scène `Settings` de SwiftUI ne s'ouvre pas depuis un `NSMenu` ; les Réglages sont une `NSWindow` qui héberge une vue SwiftUI. `MainMenu` est un menu complet (Cumulus, Fichier, Édition, Présentation, Fenêtre, Aide) : invisible tant que l'app est `.accessory`, il porte quand même ⌘, ⌘Q ⌘W ⌘0 et le menu Édition, sans lequel ⌘V ne marche pas dans les champs. La fenêtre principale est une `NSWindow` (une scène SwiftUI `Window` ne s'ouvre pas depuis un `NSMenu`), comme les Réglages ; un clic sur un build du menu l'ouvre sur ce build.

**Plusieurs comptes** (XCO-71, XCO-77) : l'app suit autant de comptes App Store Connect (équipes) qu'on lui donne de clés. **Tous se synchronisent en permanence**, chacun avec sa clé et donc son propre budget de requêtes ; **un seul est sélectionné**, et c'est lui que montrent le menu, la fenêtre et la commande `cumulus`. **Zéro compte est un état normal** (installation neuve, dernier compte supprimé) : le menu ne propose qu'« Ajouter un compte… », la fenêtre son état vide, `cumulus` répond `NO_CACHE`. Un compte n'existe qu'une fois sa clé acceptée par Apple (`NewAccountModel` teste, puis `AccountsModel.add` crée le compte et range la clé) : il n'y a jamais de compte sans clé, et le lancement efface ceux qu'une version précédente avait créés sans clé ni cache. Un compte, c'est une `AccountSession` : son `SettingsModel` (clé et forfait), son `BuildStore`, son `UsageStore`, son `BuildExtrasStore` et, pour la fenêtre, ses `AccountWindowStores`. Rien n'est partagé entre deux comptes :
- **trousseau** : même service, `kSecAttrAccount` = identifiant du compte. Le premier compte s'appelle `default` (`AccountRegistry.firstAccountID`), la valeur que portait l'élément d'avant les comptes ;
- **fichiers** : `Accounts/<id>/` dans le conteneur de groupe et `Caches/Accounts/<id>/` (`AccountPaths`). Les valeurs par défaut des stores (`BuildCacheStore()`, `LogCache()`…) pointent sur le premier compte : l'app passe toujours les chemins du compte ;
- **préférences** : `account.<id>.<clé>` (`AccountDefaults.names` : forfait, date de réinitialisation, accès de la clé, palette, état des alertes de forfait, builds bloqués déjà signalés). Une préférence par compte s'ajoute à cette liste, sinon la suppression d'un compte la laisse derrière elle. Les épinglés, les apps muettes et les réglages de notifications restent communs : ils sont indexés par des identifiants d'Apple, uniques d'un compte à l'autre.

Le registre (`Accounts.json` à la racine du conteneur de groupe : noms, identifiants, compte sélectionné ; jamais l'Issuer ID) est écrit par l'app et lu par `cumulus`. Au premier lancement sans registre, `AccountMigration` fait de l'installation existante le premier compte (fichiers déplacés, préférences reprises), seulement si elle avait une clé ou un cache. `AccountsModel.start()` est appelé **avant** que la fenêtre puisse s'ouvrir, et tout ce qui lit un cache attend `whenReady()` : un cache lu avant son déplacement serait pris pour vide et tout serait redemandé à Apple. Supprimer un compte (`AccountSession.erase`, la seule suppression qui existe, le dernier compte compris) retire sa clé, puis attend la fin d'une synchro en cours (`BuildStore.retire`) avant d'effacer ses dossiers ; si le trousseau refuse, rien n'est touché. **Les Réglages sont une fenêtre à barre latérale** (XCO-97), à la manière de Réglages Système : `SettingsWindowController` héberge `SettingsRootView`, un `NavigationSplitView`. La barre latérale liste Général, Notifications et Agents, puis chaque compte avec le point de son état (`AccountHealth`), puis « Ajouter un compte… » : un compte est une destination (`SettingsDestination`), plus une liste dans un onglet. `SettingsNavigationModel` tient le volet affiché, mémorisé par son nom sous `settings.selectedTabName` (les noms des anciens onglets sont repris) ; la fenêtre s'ouvre sur un compte tant qu'il n'y en a aucun ou que l'un d'eux réclame sa clé ou sa date. La sélection d'un compte (`AccountsSettingsModel`) est propre aux Réglages et ne change jamais le compte affiché par le menu. Le volet d'un compte (`AccountsSettingsView` puis `AccountDetailView`) porte le nom du compte en titre, son état en sous-titre et « Tester la connexion » dans la barre d'outils. Sa fiche tient en groupes courts (XCO-98) : Compte (nom, clé, accès, apps trouvées), Forfait, Minutes facturées, Dépôts locaux, puis la suppression ; un bandeau ne s'ajoute que pour une clé refusée ou un test en cours. Les guides ne s'affichent plus d'office : celui du forfait tant que la date manque, les deux derrière « Où trouver la clé et la date de réinitialisation ? » ; un compte sans clé ne montre que la saisie de la clé. La saisie d'une clé (nouveau compte, ou compte dont la clé manque) est en deux colonnes (`KeyEntryColumns`, XCO-99) : le formulaire à gauche, le guide en quatre étapes à droite, qui reste en vue ; sous 640 pt de large, le guide passe sous le formulaire. Les minutes facturées (exports importés) se lisent dans le détail du compte : il n'y a plus d'onglet Usage (XCO-78) ; un export choisi depuis le détail d'un compte va à ce compte quand ses apps ne disent rien. La fenêtre s'ouvre à 900 × 720 et garde la taille qu'on lui donne tant qu'elle reste ouverte. **Son minimum (700 × 460) est tenu par le délégué** (`windowWillResize`) : le contenu SwiftUI efface un `contentMinSize` posé sur la fenêtre (vérifié le 12/10/2026). En Debug, `XCC_SETTINGS=general|notifications|agents|accounts` ouvre les Réglages sur ce volet au lancement. Le volet Général (XCO-102) s'ouvre sur l'icône de l'app, sa version lue dans le bundle et la fraîcheur des builds du compte affiché, puis deux groupes : Démarrage et fenêtre, Langue. Changer de compte vide la sélection de la fenêtre (`NavigationModel.accountDidChange`) ; ouvrir un build d'un autre compte (menu, bannière, adresse, socket) sélectionne d'abord le compte qui le détient (`AccountsModel.owner(ofBuild:)`). Le sélecteur en tête du menu (`AccountSwitcherControl`, absent avec un seul compte) est dessiné en SwiftUI mais prend ses clics en AppKit (`mouseUp`), et le menu se reconstruit sous lui sans se fermer. Le clavier n'atteint pas une vue de menu : ⌘1 à ⌘9 sont portés par des items masqués (`allowsKeyEquivalentWhenHidden`, XCO-76), et le menu se ferme comme sur tout raccourci ; VoiceOver lit un groupe de boutons radio (`AccountSwitcherElement`, un par compte, posé là où il est dessiné), le dessin SwiftUI lui étant caché. La pastille de la barre parle pour tous les comptes : un build en cours quelque part, sinon un échec quelque part. Un export d'usage ne nomme pas son équipe : `UsageImportRouting` l'envoie au compte dont il liste les apps ; s'il n'en liste aucune connue, il n'est pas importé tout seul, et va au compte affiché quand l'utilisateur le choisit à la main. Les tests passent par `TestAccounts` (dossier temporaire, trousseau en mémoire) ; sous tests, `AppDelegate` ne migre rien.

**Cible `cumulus`** (XCO-57, vérifié le 10/10/2026) : un outil en ligne de commande (bundle ID `com.guik.xcode-cloud-companion.cli`, Info.plist embarqué dans le binaire), signé avec **sa propre** sandbox et l'app group `4HYT2U85R2.com.guik.cumulus` (`Config/cumulus-cli.entitlements` ; l'app porte le même groupe par `Config/Cumulus.entitlements`). Un helper signé « inherit » serait tué dès qu'on le lance depuis un terminal. Il ne lit ni le trousseau ni le réseau : seulement ce que l'app écrit dans le conteneur de groupe (`SharedContainer.applicationSupport` : `Accounts.json`, puis par compte, dans `Accounts/<id>/`, `BuildCache.json`, `UsageLedger.json`, `UsagePlan.json`, `BuildDetails/`, `WorkflowDetails/`). `CacheMigration` y déplace une fois les caches d'avant. Le forfait vit dans les préférences de l'app, hors de portée du CLI : le `SettingsModel` de chaque compte en tient une copie par `SharedPlanStore`. Les fichiers de l'app que le CLI compile sont listés un par un dans `project.pbxproj` (`PBXFileSystemSynchronizedBuildFileExceptionSet` de la cible `cumulus`) : un nouveau fichier partagé s'y ajoute à la main ; aucun fichier qui importe AppKit ou SwiftUI.

**Contrat de la commande `cumulus`** (XCO-58) : `status`, `accounts`, `apps`, `builds`, `build <App#42 | id>`, `workflows`, `usage`, `open`, `refresh [--wait]`, `run <workflow>` (XCO-61). JSON dans un tube, tableau sur un terminal (`--json` / `--table`). Chaque commande répond pour le compte sélectionné dans l'app, ou pour celui que nomme `--account <nom>` (`CLIAccountScope` ; `accounts` les liste). Enveloppe `{ data, meta }` ; `meta.lastSuccessfulSync` dit l'âge du cache, `meta.appRunning` si l'app répond sur son socket, `meta.isEstimate` signale des minutes estimées, et `meta.account` nomme le compte de la réponse. Erreurs sur stderr (`{ error: { code, message, suggestions } }`), codes de sortie 0, 1, 2 (usage), 3 (pas de cache ou pas de clé), 4 (app injoignable), 5 (introuvable ou ambigu), 6 (délai dépassé), 7 (clé en lecture seule ou 403, `run`), 8 (plafond de lancements ou limite d'Apple, `run`). Les noms de propriétés des types de `CLI/CLIModels.swift` **sont** les clés JSON publiques : en renommer une casse les agents, et `CLICommandTests` le signale. Sortie en anglais, hors catalogue de traduction. `CLIQueryRunner` répond à une `CLIQuery` ; la ligne de commande et le serveur MCP passent tous deux par lui.

**Socket entre l'app et `cumulus`** (XCO-59, vérifié le 10/10/2026) : l'app écoute un socket Unix `ipc.sock` à la racine du conteneur de groupe, le seul endroit où la sandbox en permet un (`IPCSocketServer`, POSIX + Dispatch ; le chemin tient en 103 octets, d'où la racine et un identifiant de groupe court). Un objet JSON par ligne dans chaque sens (`CLI/IPC/`) : `ping`, `refresh { wait }`, `open { buildRunID }`, `loadDetails { buildRunID }`. `ping`, `refresh` et `launch` acceptent un `accountID` (le compte sélectionné sinon) ; `open` et `loadDetails` trouvent seuls le compte du build. Seule `launch` écrit chez Apple (XCO-61, voir « Lancer depuis un agent »). `AppIPCService` refuse une synchro de moins de 30 s (`recent`) et n'en lance pas une seconde (`syncing`). `loadDetails` charge les problèmes, tests et artefacts d'un build terminé comme le fait sa fiche : c'est ce qui permet à `cumulus build` de répondre sur un build jamais ouvert dans la fenêtre. Un socket accepté hérite du mode non bloquant de l'écoute sur macOS : il est remis en bloquant. Les attentes sur socket se font sur une file Dispatch, jamais sur le pool de concurrence Swift. Une seconde instance de l'app laisse le socket de la première ; le serveur ne démarre pas sous tests.

**Serveur MCP** (XCO-60, vérifié avec Claude Code le 10/10/2026) : `cumulus mcp` parle Model Context Protocol sur stdio, écrit à la main dans `CLI/MCP/` (JSON-RPC 2.0, un message par ligne ; `initialize`, `ping`, `tools/list`, `tools/call` ; versions 2025-03-26, 2025-06-18 et 2025-11-25). Neuf outils, chacun rendant le JSON de la commande correspondante en texte et en `structuredContent` : `get_status`, `list_apps`, `list_builds`, `get_build`, `list_workflows`, `get_usage`, `refresh`, `start_build`, `list_accounts`. Tous sauf le dernier prennent `account`, l'équivalent de `--account` (`MCPTool.takesAccount`). Une erreur métier est un résultat `isError: true` que le modèle lit, jamais une erreur JSON-RPC. Rien d'autre que le protocole ne s'écrit sur stdout ; `--verbose` journalise sur stderr. Un outil s'ajoute dans `MCPTools.all`, avec sa description écrite pour un agent ; `start_build` est le seul qui lance un build (`idempotentHint: false`), aux conditions ci-dessous.

**Cumulus Pro** (XCO-132, XCO-135, 13/10/2026) : l'app est gratuite pour un compte ; Cumulus Pro se paie 19,99 € par an avec un mois d'essai, ou 59,99 € à vie, par StoreKit 2, sans serveur ni dépendance. Deux produits (`ProProduct`) : `com.guik.cumulus.pro.yearly`, dans le groupe d'abonnements « Cumulus Pro », et `com.guik.cumulus.pro.lifetime`, non consommable ; un identifiant de produit ne prend pas de tiret et ne se change jamais. `ProStore` (`Pro/`, créé par `AppDelegate`) est **le seul endroit qui dit si Pro est ouvert** : vues et modèles ne posent que `allows(_:)`, avec un cas de `ProFeature`, la liste fermée des fonctions Pro (la répartition décidée est dans XCO-132 ; au 13/10/2026 aucun verrou n'est encore posé). L'état (`ProEntitlement` : gratuit, essai, abonné, à vie, expiré) est un calcul pur sur les transactions (`ProEntitlement.resolve`) : une transaction que StoreKit n'a pas vérifiée n'ouvre rien, l'achat à vie l'emporte sur tout abonnement, la période de grâce et la relance de facturation gardent Pro ouvert, un abonnement fini ou remboursé donne « expiré » et non « gratuit ». **Rien n'est écrit dans les préférences** : StoreKit garde les transactions vérifiées sur le Mac, l'état est donc connu hors ligne. `StoreKitProSource` lit `Transaction.currentEntitlements` (et `Transaction.latest` pour un abonnement fini, qui n'y figure plus), suit `Transaction.updates` et `Product.SubscriptionInfo.Status.updates` ; `ProStore` relit aussi juste après la fin d'une période, qui n'amène pas toujours de transaction. Sous tests, `AppDelegate` ne démarre pas l'écoute. En Debug, `XCC_PRO=0|1|trial|lifetime|expired` fige l'état sans rien lire. `xcode-cloud-companionTests/Cumulus.storekit` décrit les deux produits : copié dans le bundle de tests pour `SKTestSession`, et branché sur le lancement du scheme `Cumulus` (branchement non vérifié depuis Xcode). **Piège des tests d'achat** (vérifié le 13/10/2026) : dans un test hébergé par l'app, ce que la session fait de son côté (`buyProduct`, `expireSubscription`, `refundTransaction`) n'arrive pas à StoreKit dans le processus : aucun événement `Transaction.updates`, et les requêtes gardent leur première réponse. Un test achète donc par `ProStore.purchase` (dialogues coupés) et appelle `ProStore.restore()` après un geste de la session. **Chaque test d'achat vide ses transactions en sortant** (`defer { session.clearTransactions() }`) : un achat laissé dans le magasin local est lu comme vrai par une app de Debug lancée ensuite, hors de Xcode compris, qui se croit alors Pro et l'écrit dans `Pro.json` (vu le 13/10/2026). La cible de tests passe `-Xcc -iframework` sur les frameworks de la plateforme : sans cela, un en-tête de StoreKitTest émet un avertissement de dépréciation à chaque compilation.

**Widgets** (XCO-49, styles choisis sur maquettes le 13/10/2026) : la cible `CumulusWidgets` (extension WidgetKit, `Widgets/`, bundle ID `com.guik.xcode-cloud-companion.widgets`, embarquée dans `Contents/PlugIns`, sa propre sandbox et le même app group par `Config/CumulusWidgets.entitlements`) propose quatre widgets : « Latest Build » (petit, réglable sur une app), « Cycle » (petit, l'anneau), « Cycle and Builds » (moyen, la barre) et « Cycle Ring and Builds » (moyen, l'anneau). **L'extension ne lit qu'un fichier** : `Widgets.json` à la racine du conteneur de groupe (`WidgetSnapshot`, dans `CLI/`), que l'app écrit pour le compte affiché après chaque synchro et à chaque changement de compte (`WidgetFeed`, `WidgetFeedWriter` dans `AppDelegate` ; rien sous tests). Elle n'a ni clé, ni réseau, ni les préférences de l'app : les couleurs des apps, le pourcentage du cycle (le même arrondi que partout) et les builds y sont déjà résolus ; les widgets ne sont rechargés (`reloadAllTimelines`) que si ce contenu a changé. Pendant la mesure et sans forfait, un widget de cycle le dit au lieu d'un chiffre. Un clic ouvre `cumulus://build/<id>` ou `cumulus://overview`. La cible **n'a pas** l'isolation `MainActor` par défaut (WidgetKit appelle ses fournisseurs hors du fil principal) et ne compile que trois fichiers partagés, listés à la main dans `project.pbxproj` : `CLI/WidgetSnapshot.swift`, `Menu/UsageFormat.swift`, `Sync/SharedContainer.swift`. Ses chaînes sont dans `Widgets/Localizable.xcstrings`. Le rendu se vérifie en copiant `WidgetViews.swift` dans un test jetable (les vues ne sont pas dans le module de l'app).

**App Intents** (XCO-62, 13/10/2026) : trois intents dans `Intents/` pour Siri, Spotlight et Raccourcis : « Get Latest Build » (paramètre d'app facultatif), « Get Running Builds », « Get Cycle Usage », avec leurs App Shortcuts (`CumulusShortcuts`). Aucun ne lance ni ne change un build. Ils lisent les caches par `IntentAnswers`, qui pose les mêmes questions que la commande (`CLIQueryRunner`), sans socket ni réseau ; la consommation se dit toujours comme une estimation tant qu'il reste des minutes estimées. **Isolation** : les entités (`BuildEntity`, `FollowedAppEntity`) sont `nonisolated` et n'ont pas de `@Property` (l'enveloppe est une référence non `Sendable`) ; un intent à `@Parameter` ne peut pas être `nonisolated` en entier : son `title`, sa `description` et son `init()` le sont un par un, `perform()` reste sur le `MainActor`. Un test crée et lit intents et entités depuis une tâche détachée. Les phrases des raccourcis se traduisent dans `AppShortcuts.xcstrings` (un `stringSet` par raccourci, sous la clé de sa première phrase, `${applicationName}` tel quel) ; les titres et les réponses sont dans `Localizable.xcstrings`. L'indexation Spotlight des builds n'est pas faite.

**Lancer depuis un agent** (XCO-61, décision de l'utilisateur le 11/10/2026) : `cumulus run <workflow> [--branch | --tag | --pr] [--clean] [--yes]` et l'outil MCP `start_build` passent par la méthode `launch` du socket : l'app reste la seule à écrire chez Apple, avec le `BuildLauncher` de la fenêtre (`AgentLaunchService`). La commande résout le workflow depuis le cache (`CLIReference.workflow` : nom, ou `App/Workflow` en cas d'homonymes) et, sans source, prend la branche du dernier build non-PR du workflow ; l'app résout branche, tag ou PR par `LaunchChoices`. Garde-fous : « Accès de la clé » à « Lecture + Build » (sinon `NOT_ALLOWED`, code 7 ; un 403 repasse la clé en lecture seule), au plus 3 lancements par heure et par compte, tous agents confondus (`AgentLaunchGate`, sinon `RATE_LIMITED`, code 8), les refus d'Apple en `REFUSED` (code 1) avec ses mots, jamais de second envoi. Sur un terminal, `cumulus run` demande `[y/N]` sauf `--yes` ; dans un tube ou par MCP, l'agent a décidé et l'app poste la notification « Build lancé par un agent » (réglable dans Réglages › Notifications). La règle « aucun lancement par URL ni par Raccourci » reste : seule une commande ou un outil appelé explicitement lance.

**Réglages › Agents** (XCO-64, XCO-101) : un volet des Réglages (`AgentsSettingsView`, `AgentsSettingsModel`, `AgentLinks.swift`), rangé par agent : on choisit Claude Code, Codex, Xcode ou Claude Desktop (mémorisé), et le volet liste ce qu'il lui faut avec son état (`AgentsSettingsModel.checklist(for:)`) : la commande, commune à tous, le skill pour les deux agents qui en gardent (`AgentClient.keepsSkills`), puis le serveur MCP, à copier à la main et donc jamais compté dans la progression. Il dit aussi ce qu'un agent peut faire : lire, et lancer un build aux conditions de « Lancer depuis un agent ». Chaque ligne dit son état en toutes lettres à côté de son bouton (XCO-150) : « Installé » ou « À réparer » pour la commande et le skill, « Connecté » pour le serveur MCP. L'app ne peut pas lire la configuration des agents (sandbox) : c'est `cumulus mcp` qui note, à chaque `initialize`, le nom que le client donne de lui-même et l'heure, dans `AgentConnections.json` à la racine du conteneur de groupe (`AgentConnectionsStore`, 20 noms au plus, rien d'autre que le nom et la date) ; `AgentClient.isConnection(named:)` rapproche ces noms des agents. L'agent d'Xcode ne se distingue de Claude Code que si son nom dit « Xcode » : sinon sa ligne ne prétend rien. Il installe la commande et le skill par **liens symboliques** depuis un dossier que l'utilisateur choisit dans un panneau (c'est ce choix qui ouvre le dossier à la sandbox ; un signet à portée de sécurité est gardé pour pouvoir retirer le lien plus tard) : `<dossier du PATH>/cumulus` vers `Contents/Helpers/cumulus`, `~/.claude/skills/cumulus` et `~/.codex/skills/cumulus` vers `Contents/Resources/AgentSkill/cumulus`. La sandbox laisse l'app **lire** ces liens sans autorisation, d'où l'état affiché sans rien demander (vérifié le 10/10/2026). Un lien n'est remplacé ou retiré que s'il mène dans un bundle Cumulus. Le skill (`xcode-cloud-companion/AgentSkill/cumulus/`, en anglais, copié tel quel dans le bundle par `explicitFolders` du groupe synchronisé) est la documentation que lisent les agents : `AgentSkillBundleTests` échoue si une commande, un outil MCP, un de ses arguments ou un code d'erreur n'y figure pas. Les lignes d'enregistrement du serveur MCP par client sont dans `AgentClient`. Pour Claude Desktop, « Exporter l'extension… » (XCO-63) enregistre un `.mcpb` (`MCPBundle`) : un zip écrit à la main (`ZipWriter`, entrées stockées) avec un `manifest.json` et un lanceur `server/launch.sh`, exécuté par `/bin/sh`, qui lance la commande **là où est l'app** : l'extension suit les mises à jour de l'app et ne se réexporte que si l'app change de place. Vérifié le 13/10/2026 avec `unzip -t` et un `initialize` envoyé au serveur par le lanceur ; l'installation dans Claude Desktop reste à constater à la main.

**Nom et icône d'une app** (XCO-73, vérifié sur le vrai compte le 10/10/2026) : l'interface affiche `CIProduct.displayName` (le nom du Store quand le produit est une app qui en a un, sinon le nom du produit). `product.name` **reste la clé** de la couleur d'une app (`AppPalette`), de ses minutes d'usage (l'export d'Apple parle en noms de produits) et des références du CLI (`App#42`, `--app`) : ne jamais les passer au nom du Store. Là où la place est comptée (colonne d'app du menu, ligne d'un build), `CIProduct.compact` coupe le nom à 14 caractères. L'icône vient de l'`iconAssetToken` d'un build : un gabarit `https://…mzstatic.com/…/{w}x{h}bb.{f}` servi sans authentification, dont le chemin finit par `.icns` pour une app Mac (dessinée telle quelle ; les autres sont des carrés pleins, arrondis dans l'app). Une requête au plus par jour (`BuildSynchronizer.refreshedIcons`) : `GET /v1/apps?include=builds&limit[builds]=1` tant qu'aucune icône n'est connue ou qu'une app apparaît (toutes les apps d'un coup, mais le build inclus n'est **pas** forcément le plus récent), puis `GET /v1/builds?sort=-uploadedDate&include=app` (les builds les plus récents, où se voit un changement d'icône). Les jetons vivent dans `BuildSnapshot.appIcons` (par `appID`), les images dans `Caches/AppIcons` (`AppIconCache`, un fichier par app et par jeton), chargées par `AppIconStore` pour la fenêtre. Le menu de la barre n'affiche pas d'icône.

**Couleur d'une app** (XCO-128, vérifié sur quatre vraies icônes le 13/10/2026) : une app prend la couleur dominante de son icône (`AppSwatch.icon`), sinon une des six teintes système d'`AppPalette`, comme avant : pas d'icône, ou une icône sans teinte. `IconColorExtractor` (`Usage/IconColor.swift`, pur) range les pixels opaques de l'icône réduite à 40 × 40 par teinte Oklab, chacun pesant sa saturation ; blancs, gris et noirs ne comptent pas, et sous 3 % de pixels colorés l'icône n'a pas de couleur. `AppPalette` garde la couleur lue telle quelle, avec l'empreinte de l'icône (`IconReading`, dans la préférence de la palette du compte, donc effacée avec lui) ; `swatch(for:)` la ramène dans une plage de luminosité lisible sur fond clair comme sombre (`SwatchColor.legible`, teinte inchangée). `AccountSession.readIconColors` lit les icônes après chaque synchro réussie, hors du fil principal : une fois par icône, de nouveau quand elle change, et au plus une tentative par heure pour une image introuvable ; aucune requête à l'API, seulement l'image (cache `AppIconCache`, sinon serveurs d'images). Le menu a donc les couleurs sans la fenêtre. La fenêtre prend sa palette par `AccountSession.palette(for:summary:)`, qui la fait redessiner quand une couleur arrive. Deux apps aux icônes de même teinte ont la même couleur. Une session créée sans `iconCache` (les tests) ne lit rien. **Couleur choisie** (XCO-129, choix de l'utilisateur sur maquettes le 13/10/2026) : une couleur donnée à la main passe devant celle de l'icône (`AppPalette.Choice` : une teinte système ou une couleur libre, dans la même préférence ; `AccountSession.chooseColor`, nil pour revenir à l'icône). Elle se choisit à deux endroits : le clic droit sur une app de la barre latérale (`AppColorMenu` : un `Picker` en style `.palette`, à la manière des étiquettes du Finder, puis « Autre couleur… » qui ouvre le `NSColorPanel` par `AppColorPanel`), et Réglages › compte › « Couleurs des apps » (un `ColorPicker` par app et « Revenir à l'icône »). Un changement d'icône ne touche pas à une couleur choisie.

**Ce qui a cassé** (XCO-66) : sur la fiche d'un build en échec, `RegressionGroup` compare avec le dernier build `SUCCEEDED` du même workflow, même branche d'abord (`RegressionReport.reference`). Les tests se rapprochent par action de même nom, classe et nom ; un test absent de la référence est « nouveau », pas « cassé ». Les problèmes se rapprochent par type, message et fichier, sans le numéro de ligne. Rien n'est demandé à Apple à l'ouverture : ce que `BuildDetails/` contient s'affiche (`BuildExtrasStore.loadCached`), le reste se charge au clic sur « Comparer », une action à la fois, et pas sous `SyncSchedule.criticalRemaining`. Les deux SHA ne s'affichent que si Apple les a donnés ; le lien de comparaison n'est construit que pour une adresse `github.com/<owner>/<repo>/commit/<sha>`.

**Journaux d'une action** (XCO-70, vérifié sur une vraie archive le 10/10/2026) : le bouton « Journaux » (onglet Actions, et action en échec de la frise) télécharge l'artefact `LOG_BUNDLE` de l'action avec les règles d'un artefact (`LogOpener` : adresse fraîche, `ArtifactAddress`, pas de jeton), le décompresse dans `Caches/Logs/<id de l'action>/` et ouvre le dossier dans le Finder, sans panneau d'enregistrement. Une vraie archive d'Xcode Cloud est un ZIP simple (entrées stockées ou « deflate », pas de ZIP64) : `ZipExtractor` le lit à la main avec `Compression`, sans `Process` ni dépendance. Il juge tous les chemins avant d'écrire le premier octet : une entrée absolue ou avec `..` refuse l'archive entière, un lien symbolique n'est jamais créé, une taille déclarée fausse ou au-delà du plafond aussi. Le cache est plafonné à 500 Mo, les dossiers ouverts le moins récemment partent d'abord. Les journaux d'un build `COMPLETE` déjà décompressés se rouvrent sans requête. Le bouton s'affiche pour toute action terminée tant qu'on ne sait pas qu'elle n'a pas d'archive : la liste des artefacts n'est pas demandée d'avance.

**Pourquoi un workflow coûte** (XCO-69) : dans la Vue d'ensemble, un clic sur une ligne de « Coût par workflow » déplie `WorkflowBreakdownView`. `WorkflowCostBreakdown` reprend build par build les minutes que compte `UsageCalculator` (facturées par l'export, ou estimées) et les répartit au prorata de `MachineModel.cost(of:)` : build, analyse, archive, tests par destination, préparation des machines, tests rejoués après un échec. Le total est donc celui de la Vue d'ensemble, au centième près (testé). Apple ne donne qu'un chiffre par build : la répartition est toujours modélisée, chaque poste porte un ~, et le texte dit si le total est exact ou estimé. Les constats (`Finding`) ne disent que ce que les chiffres portent, sans conseil ni promesse d'économie. Aucune requête : tout vient de l'instantané et du registre d'usage.

**Vue d'ensemble** (XCO-96) : en tête, `CycleRingGroup` : un anneau découpé par app (`OverviewModel.ring`, aux couleurs d'`AppPalette`, la part non utilisée en neutre puis orange et rouge comme la jauge du menu), le temps utilisé, le forfait et la réinitialisation, puis le rythme et l'âge de l'export dans les mots du menu (`UsageSummary.paceLine`, `exportLine` : une seule rédaction pour les deux), et la légende par app qui remplace « Minutes par app ». Pendant la mesure, l'anneau est vide et aucun chiffre qui en dépend ne s'affiche. « Coût par workflow » porte une barre empilée (`OverviewModel.workflowBar` : les huit premiers, puis « autres » en neutre ; un second workflow de la même app prend une teinte plus claire) ; « Le build le plus coûteux » en est la dernière ligne. L'import d'un export est une ligne de pied. Le menu de la barre garde `UsageGaugeView`.

**Vue d'ensemble d'une app** (XCO-107, XCO-109 à XCO-111) : une app choisie dans la barre latérale, sans build sélectionné, montre `AppOverviewView` dans la colonne de droite. De haut en bas : l'identité (icône, nom affiché, nom du produit, dépôt, dernière livraison TestFlight), le cycle en une barre (les workflows de l'app en teintes de sa couleur, les autres apps en gris), le tableau des workflows (dernier build, réussite, durée médiane, minutes du cycle, prochain passage, puis une ligne pour l'app), les 30 derniers builds terminés en barres, les branches et pull requests de l'app, et « À noter » (Xcode dépassé, build le plus coûteux, part d'estimation). Tout vient d'`AppOverviewModel` (pur) : `UsageSummary` pour les minutes (`costliestBuildByApp` pour le build le plus coûteux), `WorkflowTrends` pour la réussite et les durées, `ScheduleForecast` pour le prochain passage, `ReferencesModel` pour les références ; les mêmes chiffres qu'ailleurs, limités à l'app. Sans planification, « Prochain » dit la condition de démarrage (`AppOverviewModel.trigger`), connue par la fiche des workflows (`WorkflowDetailStore.load`, cache d'abord). Deux lectures seulement sont propres à l'écran, celles que font déjà la fiche d'un workflow et celle d'un build : les workflows de l'app, et le build TestFlight du dernier succès (`loadBetaBuilds`, une fois puis en cache, pas sous `SyncSchedule.criticalRemaining`). Les minutes des builds que l'export liste sans workflow sont dans le total et dans la barre (« Autres workflows »), pas dans une ligne du tableau. Sans forfait ou pendant la mesure, la colonne des minutes disparaît. Une colonne étroite remplace le tableau par deux lignes par workflow (`ViewThatFits`). En Debug, `XCC_APP=<nom du produit>` ouvre la fenêtre sur cet écran.

**Tests instables et tests lents** (XCO-67) : la fiche d'un workflow a une section Tests (`WorkflowTestsSection`). `TestHealthReport` (pur) lit les résultats de tests des builds terminés du workflow : un test est instable s'il est `MIXED` dans un build, ou s'il échoue et réussit sur **le même commit** ; échouer sur un commit puis réussir sur le suivant n'est pas de l'instabilité, toujours échouer non plus. Les plus lents sont classés par durée moyenne par appareil. C'est toujours un échantillon : la section dit combien de builds sont analysés sur combien. `TestHealthReader` lit `BuildDetails/` hors du fil principal, sans requête et sans garder les résultats entiers en mémoire ; « Analyser d'autres builds » charge les 10 plus récents qui manquent, un build après l'autre, s'arrête sur demande et sous `SyncSchedule.criticalRemaining`. Rien ne se charge en tâche de fond. Un clic sur un test instable ouvre le dernier build où il a échoué, onglet Tests (`NavigationModel.buildTab`).

**Notifications** (XCO-47) : locales, sans serveur ni entitlement. `AccountsModel.onSync` donne, pour chaque compte, l'instantané d'avant et d'après chaque synchro réussie ; un build « vient de finir » quand il était en cours avant et `COMPLETE` après (ou créé puis terminé entre deux synchros), depuis moins d'une heure. La première synchro d'un compte dans une session ne notifie rien. Tous les comptes notifient, quel que soit celui affiché ; avec plusieurs comptes, la bannière porte le nom du sien en sous-titre. L'autorisation n'est demandée qu'au moment d'envoyer la première bannière, ou par le bouton de l'onglet Notifications des Réglages : jamais au lancement. Un build bloqué (action `RUNNING` au-delà de N fois la médiane de la même action réussie du workflow, trois échantillons au moins) est signalé une fois, y compris après un redémarrage. Le clic ouvre l'adresse `cumulus://` portée par la bannière. `NotificationResponder` est `nonisolated` : le centre de notifications l'appelle hors du fil principal. Le délégué n'est posé que hors tests, et les tests passent par un `NotificationPosting` simulé. En Debug, `XCC_NOTIFY=1` poste une bannière d'essai après la première synchro.

**Volet Notifications** (XCO-100) : l'autorisation est un bandeau en tête (vert quand macOS laisse passer les bannières, sinon le bouton qui y mène) ; les états de fin de build portent leur glyphe (`StatusBadge`), le seuil de blocage est un sélecteur segmenté sur `BuildNotificationRules.stuckFactors`, et chaque app a son icône ou son initiale. Aucune préférence n'a changé de clé.

**Alerte de forfait** (XCO-65) : `UsageAlertPlanner` lit le même `UsageSummary` que le menu, après chaque synchro : 75 % puis 90 % du forfait, et le rythme (`exhaustionDate`). Une alerte par seuil, par cycle et par compte, mémorisée dans les préférences (`UsageAlertState`) et remise à zéro quand le cycle change ; rien pendant la mesure du premier chargement ni sans forfait. Chaque message dit que le chiffre est une estimation tant qu'il reste des minutes estimées ou que l'export a plus de trois jours. Le clic ouvre `cumulus://overview?account=<id>`, la Vue d'ensemble du compte concerné.

**Piège d'isolation** (vérifié le 10/10/2026) : dans ce module à isolation `MainActor` par défaut, une fermeture écrite dans une fonction `nonisolated` d'un type `MainActor` (une vue, par exemple) reste isolée au `MainActor` et **plante à l'exécution** hors du fil principal (`dispatch_assert_queue`). Mettre ce code dans un type `nonisolated`. Le lanceur de tests relance l'hôte et affiche quand même « passed » : après un doute, compter les rapports `Cumulus-*.ips` dans `~/Library/Logs/DiagnosticReports`.

**Source des minutes** (XCO-6, mesuré sur 55 builds réels le 09/10/2026) : Apple facture **par machine**. Chaque destination de test paie son temps d'exécution (`destinationTestResults[].duration`, sommé par appareil) plus ~4,5 min de préparation, et deux fois ses tests quand l'un d'eux échoue (rejoué) ; une archive réussie paie son calcul seul, pas l'envoi à TestFlight : on prend son passage réussi le plus court. Le tout dans `MachineModel`. Résultat : +2 % sur 30 jours, 4 min d'écart moyen par build, sauf certains échecs rejoués (jusqu'à −40 min). La durée murale d'un test ne dit **ni** le nombre de simulateurs **ni** leur attente : ne jamais l'additionner. L'export CSV d'Apple (XCO-14) reste la source exacte quand il est importé.

**Pièges de la barre des menus** (vérifiés sur le vrai bouton le 09/10/2026) :
- L'image du bouton vient des symboles du catalogue (`MenuBarIcon`) : `logo` seul en template, ou `logo.badge` en palette (pastille = niveau primaire, à la couleur de l'état ; nuage = niveau secondaire, à la couleur du texte résolue **au dessin**, sinon il prend l'apparence de l'app et non celle de la barre). Les deux se chargent par `NSImage(symbolName:bundle:)` : l'icône d'app s'appelle aussi « logo ». Aucune vue n'est posée sur le bouton.
- Une icône ajoutée alors que la barre est pleine est **masquée** (icône « « » de débordement) : pour voir sa propre instance, libérer de la place ou quitter une autre instance de l'app.
- En Debug, `XCC_BADGE=running|failed|succeeded|stopped|none` force la pastille de la barre.
- `NSMenuItem.badge` n'accepte ni couleur ni style : l'âge des builds et les minutes des apps y sont des textes courts ; les points d'état et le carré de couleur d'une app sont des caractères teintés (« • », « ◉ », « ■ ») en tête du titre attribué : le menu n'affiche **aucune** `NSMenuItem.image` (ni dessinée, ni symbole SF), vérifié le 09/10/2026.

**Écriture : lancer ou relancer un build** (XCO-43, la première des deux requêtes qui modifient quelque chose chez Apple) : `POST /v1/ciBuildRuns`, **jamais rejouée par l'app**, même après un timeout ou un 5xx. Un échec ambigu relit d'abord `GET /v1/ciWorkflows/{id}/buildRuns?limit=1&sort=-number` (`BuildLauncher`), l'interface ne propose un nouvel essai qu'après. **Une réponse 2xx vaut lancement, quoi qu'on sache lire de son corps** (XCO-127 ; vu le 12/10/2026 dans le journal système : Apple a répondu 201, le corps n'a pas décodé, et la liste relue une demi-seconde plus tard ne montrait pas encore le build) : `startBuildRun` rend le build dès que son identifiant se lit, et la liste est relue jusqu'à quatre fois (`BuildLauncher.lookDelays` : tout de suite, puis 2, 4 et 8 s ; arrêt sur un 429). Trois issues se distinguent : `.accepted` (2xx, pas encore listé : ne pas relancer), `.uncertain(found: nil)` (liste lue, aucun nouveau build), `.unknown` (liste illisible : on ne sait pas). Ce qui n'a pas pu être lu part au journal système (`LaunchLog`, sous-système `com.guik.xcode-cloud-companion`, catégorie `launch`) : `/usr/bin/log show --predicate 'subsystem == "com.guik.xcode-cloud-companion"'` (dans zsh, `log` seul est une commande interne). Le corps n'envoie `clean` que s'il vaut `true`, un lancement a une seule source (branche/tag ou PR), une relance aucune. La feuille de lancement (XCO-48) propose les branches, les tags et les pull requests ouvertes du dépôt du workflow (`LaunchChoices` : `gitReferences` puis `GET /v1/scmRepositories/{id}/pullRequests`, filtré sur `isClosed`), lus une fois par session par `BuildLauncher.choices` ; si la liste des PR échoue, branches et tags restent proposés. Sous le menu, `LaunchSourceHistory` dit le dernier build du cache sur cette source ; au-delà de 12 noms un champ filtre la liste, qui n'en affiche jamais plus de 60. Le réglage « Accès de la clé » (Réglages › Comptes, `KeyAccess`, XCO-74, propre à chaque compte : `SettingsModel.keyAccess`) vaut « Lecture + Build » par défaut : chaque écriture passe déjà par une confirmation, et masquer les boutons les rendait introuvables. L'utilisateur peut choisir « Lecture seule » ; un 403 y repasse tout seul, et supprimer la clé remet la valeur par défaut. Aucun lancement par URL ni par Raccourci. Le schéma `cumulus://build/<id>` et `cumulus://overview[?account=<id>]` (lecture seule, `CumulusURL`) est déclaré par `Config/URLScheme.plist`, fusionné à l'Info.plist généré (`INFOPLIST_FILE` + `GENERATE_INFOPLIST_FILE`) : `CFBundleURLTypes` ne se pose pas par `INFOPLIST_KEY_*`.

**Écriture : mettre un workflow en pause** (XCO-68, la seconde et dernière écriture) : `PATCH /v1/ciWorkflows/{id}` dont le corps ne porte que `isEnabled` (`WorkflowStateRequest`), **jamais rejouée**. `WorkflowPauser` suit les règles du lancement : confirmation qui nomme le workflow, visible seulement si « Accès de la clé » vaut « Lecture + Build » (même valeur `KeyAccess.canLaunch` que le lancement), un 403 repasse la clé en lecture seule, 409 et 422 montrent les mots d'Apple. L'état affiché est celui de la réponse d'Apple, jamais celui qui a été demandé ; une réponse sans état ou un échec ambigu sont suivis d'une **lecture** (`GET` du workflow, champ `isEnabled` seul), pas d'un second essai. Un workflow verrouillé (`isLockedForEditing`) ne propose pas l'action. La synchro demande `isEnabled` et `isLockedForEditing` avec les workflows, sans requête de plus ; `BuildStore.setWorkflowEnabled` garde la réponse d'Apple contre une synchro commencée avant elle. Le rôle de clé requis n'est pas documenté : l'essai réel est fait par l'utilisateur, les agents n'envoient pas cette écriture.

**Durées de ce qui tourne** (XCO-80) : la fenêtre se redessine à la minute, sauf ce qui tourne. Dans la liste, seule la durée d'un build en cours avance à la seconde (`BuildCard.runningSince`) ; la fiche d'un build non terminé se redessine entière chaque seconde (`BuildDetailView.redrawInterval`), ce qui fait avancer la frise et le temps écoulé. Tout se calcule depuis le début lu chez Apple : une synchro ne fait pas sauter le compteur, et il s'arrête quand elle dit le build terminé. Le menu de la barre n'affiche que des minutes et ne bouge pas tant qu'il est ouvert.

**Carte d'un build** (XCO-93) : dans la liste, une carte (`BuildCard`) porte l'icône de l'app, la première ligne du message du commit en titre (`BuildRowData.commitTitle`, lu dans `sourceCommit` déjà en cache), puis `#numéro · état · workflow · branche`, l'état seul en couleur (`BuildStatus.textTint`, rapprochée de la couleur du texte pour rester lisible). Sans message, le titre redevient l'état. Le badge d'état a quitté la carte : le rail porte le point (`TimelineRow`), un symbole `circle.fill` qui respire en continu tant que le build tourne (XCO-106), et reste fixe sinon ou avec « Réduire les animations ». La vue Branches et pull requests dessine la même carte (`BuildCard(reference:)`), titrée par la référence. La recherche trouve aussi un build par son message.

**Fiche d'un build** (XCO-94) : une seule carte d'identité en tête (`BuildDetailView.identityCard`) : icône de l'app sans pastille, numéro, capsules (l'état dit le nombre de tests en échec, `BuildDetailModel.statusText`), la durée en grand et l'âge à droite, puis les faits en grille. La durée n'est plus un fait (`clockDuration`). Le coût vient d'`UsageCalculator.cost(of:in:ledger:now:)`, la règle du cycle appliquée à un build : minutes facturées si un export le liste, sinon estimation avec « ~ », rien pour un build en cours ou dont les résultats de tests ne sont pas encore lus. Un fait inconnu est omis. La frise est à plat, le commit en citation ; « Comparer avec #n » y déclenche la comparaison du groupe « Ce qui a cassé » (`RegressionGroup.compareRequest`). Les onglets sont des pastilles (`PillButtonStyle`) : le style verre de SwiftUI ne se dessine pas dans un rendu hors écran, il n'a donc pas pu être vérifié et n'est pas utilisé là.

**Taille de la fenêtre principale** (XCO-108, vérifié le 12/10/2026) : `MainWindowController` vide `sizingOptions` du contrôleur d'hébergement, comme les Réglages. Laissé à lui-même, celui-ci ramène la fenêtre à la taille minimale de son contenu (591 × 190 points), et c'est cette taille qui s'enregistre sous `MainWindow`, pour toutes les instances. La fenêtre s'ouvre à 1180 × 740 la première fois, puis à la taille enregistrée ; son minimum (900 × 560) est tenu par `windowWillResize`, et une taille enregistrée plus petite s'ouvre au minimum. Sous tests, le contrôleur reçoit `frameName: nil` pour ne rien lire ni écrire dans les préférences, et un test demande sa fenêtre au contrôleur (`controller.window`), pas par son titre : plusieurs tests en ouvrent une en même temps.

**Fiches sur une ou deux colonnes** (XCO-113) : aucune fiche de la colonne de droite n'a de largeur plafonnée. `DetailScroll` (`Window/Components/DetailColumns.swift`) porte le défilement et dit à la fiche combien de colonnes elle a : deux à partir de 880 pt (`DetailColumns.threshold`, marges de 24 pt comprises), **mesurés sur la colonne de la fiche**, pas sur la fenêtre : masquer la barre latérale ou élargir la liste des builds compte. Seul le mode est gardé en état, pas la largeur : la fiche ne se redessine qu'au passage du seuil. Les groupes sont les enfants directs d'un `Layout` (`DetailColumnsLayout`) et disent leur place par `.detailPlacement(.full | .main | .side)` ; sur une colonne ils se suivent dans l'ordre déclaré, et une rangée qui n'a rien d'un côté prend toute la largeur. `DetailColumnsGeometry` (pur, testé) calcule les emplacements. **Ne pas remplacer ce `Layout` par deux piles choisies par un `if`** : au passage du seuil, un groupe changerait d'identité, perdrait son état et relancerait ses `.task`, donc des requêtes. Seul un groupe sans état ni tâche peut changer de forme selon le mode (`if columns == .two`).

**Fiche d'un build sur deux colonnes** (XCO-114) : à gauche la carte d'identité, qui porte alors la frise sous son séparateur, puis les onglets ; à droite le commit en carte, « Ce qui a cassé », TestFlight et les faits, deux par ligne. Sur une colonne, la fiche de XCO-94 est inchangée (faits dans la carte, frise à plat, commit en citation). La frise (`ActionsFrieze`) ne déborde jamais : ses étapes se resserrent de 120 à 84 pt, puis elle passe sur plusieurs rangées (`rowSizes`, par `ViewThatFits`). Dans une colonne étroite (320 pt à la largeur minimale de la fenêtre), l'en-tête de la carte met les capsules sous le numéro, les pastilles des onglets vont sur deux rangées, et les liens du commit les uns sous les autres. VoiceOver lit la colonne de gauche d'abord (`accessibilitySortPriority`).

**Vue d'ensemble sur deux colonnes** (XCO-115) : le titre sur toute la largeur ; à gauche l'anneau et « Coût par workflow » ; à droite « À venir », « Le build le plus coûteux » et « Export d'usage », en cartes. Sur une colonne, l'écran de XCO-96 est inchangé : le build le plus coûteux est la dernière ligne de « Coût par workflow », l'import une ligne de pied. Dans une colonne étroite, l'anneau passe au-dessus de ses chiffres (`CycleRingGroup`, `ViewThatFits`) et une ligne de « À venir » s'écrit sur deux lignes.

**Vue d'ensemble d'une app par moitiés** (XCO-116) : cet écran ne suit pas le partage « principale + 340 pt », le tableau des workflows ayant besoin de 600 pt pour rester un tableau. À partir de 880 pt : l'en-tête sur toute la largeur, puis le cycle et les 30 derniers builds à parts égales, le tableau sur toute la largeur, puis « Branches et pull requests » et « À noter » à parts égales (`DetailScroll(sideWidth: nil, equalHeights: true)` : deux groupes côte à côte prennent la hauteur du plus grand, d'où le `maxHeight: .infinity` de leurs cartes). Sous 880 pt, l'écran de XCO-110 et XCO-111 est inchangé.

**Fiche d'un workflow sur deux colonnes** (XCO-117, découpage proposé par l'agent, sans planche) : le bandeau de version d'Xcode sur toute la largeur ; à gauche l'en-tête, les Tests et les Tendances ; à droite les faits (deux par ligne), les conditions de démarrage et les actions. Sans Tests ni Tendances, tout reste sur une colonne. Une condition de démarrage trop longue pour sa ligne passe sous son titre.

**Réglages sur deux colonnes** (XCO-118, vérifié le 12/10/2026) : à partir de 880 pt de volet (une fenêtre d'environ 1 100 pt), `SettingsColumns` partage les sections d'un volet entre deux `Form` groupés côte à côte, à parts égales, dans **un seul** `ScrollView` : chaque formulaire a son défilement coupé (`scrollDisabled`) et prend la hauteur de ses sections (`fixedSize(vertical:)`). En dessous, un seul formulaire, dans l'ordre d'avant. **Une section ne s'étend jamais sur les deux colonnes** : un `Form` groupé plafonne sa propre largeur vers 700 pt et se centre, une section posée au-dessus de deux moitiés serait plus étroite qu'elles ; ce qui ouvre un volet (bandeau d'autorisation, clé refusée) est en tête de la colonne de gauche. Seul un `header` passe en travers du volet, parce que `SettingsColumns` le dessine lui-même et pas un formulaire (carte aux mesures du système relevées sur capture : marge de 20 pt, rayon de 10, fond à 3 % de la couleur du texte) : c'est le cas de la ligne « Cumulus » du volet Général (demande de l'utilisateur, 12/10/2026). Partage : Général (en-tête sur toute la largeur, puis Démarrage et fenêtre | Langue), Notifications (autorisation, fin de build, build bloqué | agents, forfait, apps), Agents (présentation, ce qu'un agent peut faire | choix de l'agent et ce qu'il lui faut), compte (Compte, Dépôts locaux | Forfait, Minutes facturées, suppression ; chaque guide s'ouvre sous le groupe qu'il explique). Les deux formulaires changent d'identité au passage du seuil : une `.task` se pose sur `SettingsColumns`, jamais dans une section. La saisie d'une clé (`KeyEntryColumns`) n'est pas concernée.

**Bouton de barre latérale** (XCO-103, vérifié le 12/10/2026) : une scène SwiftUI reçoit d'office le bouton qui affiche et masque la barre latérale ; une `NSWindow` qui héberge un `NavigationSplitView` ne le reçoit pas. La fenêtre principale et les Réglages le posent donc eux-mêmes (`SidebarToggleButton`, placement `.navigation`), sur la liaison `columnVisibility` de leur vue, qui part de `.all` : `.automatic` se compare égal à `.doubleColumn` et se lirait comme une barre masquée. La commande du menu Présentation (⌃⌘S) agit sur la même vue.

**Actualiser** (XCO-104) : la partie de la barre d'outils qui surmonte la barre latérale porte, à droite, `RefreshButton` : un bouton qui synchronise le compte affiché (`BuildStore.refreshNow`). Son symbole est celui d'une action en cours de la frise ; tant qu'une requête est en cours, il tourne (effet `rotate`, répété sans délai) et le bouton ne prend plus de clic, sans être grisé. Avec « Réduire les animations », l'indicateur du système le remplace. `RefreshControl.current` (pur) décide : la synchro du compte, ou ce que la fenêtre lit pour elle-même (fiche du build sélectionné, builds plus anciens, pull requests ouvertes). Rien ne part de ce bouton pendant ce temps ; il est aussi désactivé, avec la raison en infobulle, après un 429 (un refus de plus doublerait l'attente) et sous `SyncSchedule.criticalRemaining`. L'item est déclaré sur la colonne de la barre latérale, après un `ToolbarSpacer(.flexible)` : c'est ce qui le range dans sa zone, et à droite (vérifié le 12/10/2026).

**Pas de `TimelineView`** (vérifié le 11/10/2026) : quand l'app n'est pas au premier plan, SwiftUI appelle la fermeture d'un `TimelineView` sur sa file `com.apple.SwiftUI.DisplayLink`, hors du fil principal. Une fermeture qui lit quoi que ce soit du `MainActor` plante alors (`dispatch_assert_queue`), et les compteurs ne défilent pas dans une fenêtre regardée du coin de l'œil. Tout ce qui dépend de l'heure passe par `TickingView` (`Window/Components`) : l'heure est un état de la vue, mis à jour par une tâche du `MainActor`, calée sur la seconde ou la minute (`TickSchedule`).

**Rythme des synchros** (XCO-81, choix de l'utilisateur le 11/10/2026) : deux rythmes seulement (`SyncSchedule`), 30 s tant qu'un build tourne ou que des résultats de tests restent à lire, 1 min le reste du temps, que la fenêtre soit ouverte ou non et l'écran verrouillé ou non ; une erreur se retente au rythme d'une minute. Seuls les garde-fous de la clé s'y ajoutent : 15 min doublées à chaque 429, ralentissement quand le budget horaire baisse (×2 sous 50 %, ×4 sous 25 %, ×8 sous 10 %, ×20 sous 50 requêtes), 2 h au plus. La fenêtre et le déverrouillage ne changent pas le rythme : ils déclenchent seulement une synchro immédiate quand la dernière n'est pas fraîche.

**Barre latérale** (XCO-82, XCO-95) : en tête de la liste, la carte du cycle (`CycleCard` : un anneau de 48 pt, les minutes, la date de réinitialisation) ; sans date de réinitialisation il n'y a pas de cycle, et `CyclePromptCard` prend sa place et mène aux Réglages (XCO-84). **L'état appartient à un workflow, pas à une app** (remarque de l'utilisateur, 11/10/2026) : l'icône d'une app n'a pas de pastille, chaque workflow porte le point de son dernier build (`SidebarContent.Workflow.lastStatus`, `StatusDot` : creux sans build, cerclé quand il tourne), et « en pause » s'écrit à droite. Les produits sont toujours dépliés, sans chevron. « Tous les builds » signale un build en cours par un point bleu. Au pied, une seule ligne de hauteur fixe : `SyncActivityView` dit ce que l'app fait pour le compte affiché (`SyncActivity.current`, la même lecture que le menu : « Mis à jour il y a 40 s », l'étape en cours, une erreur) et, s'il reste de la place, le budget de requêtes en quelques caractères (le détail en infobulle). Elle ne devient une carte, avec progression et temps restant, que pendant la première synchro et la mesure des builds. `AccountSession.measurement` donne la même mesure au menu et à la fenêtre. **Jamais de `fixedSize(vertical:)` dans le pied de la barre latérale** (XCO-85, vérifié le 11/10/2026) : pour connaître sa taille minimale, la fenêtre ne propose aucune largeur à son contenu ; un texte à hauteur fixe se met alors un mot par ligne, et sa hauteur devient le minimum de toute la fenêtre, qui ne se réduit plus. `lineLimit` suffit.

**Builds plus anciens** (XCO-53) : le cache garde 35 jours de builds. Au pied de la liste (toutes les apps, une app ou un workflow ; pas une référence), « Charger les builds plus anciens » demande la page suivante de `GET /v1/ciProducts/{id}/buildRuns` (`OlderBuildsStore`, par compte dans `AccountWindowStores`) : une page par clic, trois au plus quand les premières ne font que répéter le cache, `links.next` gardé par produit, rien sous `SyncSchedule.criticalRemaining`, aucun nouvel essai après un 429. Ces builds restent **hors de l'instantané** (`BuildListModel.olderRuns`) : ni cache sur disque, ni minutes du cycle, ni notifications ; ils disparaissent avec la fenêtre du compte.

**Ouvrir un fichier dans Xcode** (XCO-91, vérifié le 11/10/2026) : Apple nomme les fichiers d'un problème ou d'un test comme la machine de build les voit (`/Volumes/workspace/repository/…`). `RepositoryFileLocator` en tire le chemin dans le dépôt (ce qui suit `repository/`, jamais de `..`) et le pose dans le clone local ; `LocalRepositories` (une par compte, `AccountDefaults.localRepositories`) garde le dossier choisi dans un panneau pour chaque app (clé : nom du produit), en signet à portée de sécurité, et le lève à chaque ouverture. `SourceOpener` ouvre le fichier à la ligne avec le `xed` **d'Xcode** (`Xcode.app/Contents/Developer/usr/bin/xed`, par `Process`) : `/usr/bin/xed` est un shim `xcrun` qui refuse de tourner dans la sandbox. Si le lancement échoue, `NSWorkspace` ouvre le fichier sans la ligne. Le bouton « Ouvrir dans Xcode » des onglets Problèmes et Tests vient par l'environnement SwiftUI (`\.sourceOpening`, posé par `MainWindowView` pour l'app du build) ; il est absent sans Xcode. Les dossiers se voient et se changent dans Réglages › Comptes › « Dépôts locaux ».

**Écriture : retoucher un workflow** (XCO-90, la troisième écriture) : `PATCH /v1/ciWorkflows/{id}` dont le corps ne porte **que ce qui a changé** (`WorkflowUpdateRequest.changes` : nom, description, `clean`, relations `xcodeVersion` et `macOsVersion`), **jamais rejouée**. `WorkflowEditor` suit les règles du lancement et de la pause : « Modifier… » visible seulement si « Accès de la clé » vaut « Lecture + Build » et si le workflow n'est pas `isLockedForEditing`, 403 → lecture seule, 409 et 422 montrent les mots d'Apple ; un échec ambigu est suivi d'une **lecture** (`GET` du workflow avec ses versions), pas d'un second essai. L'état affiché est celui de la réponse d'Apple, qui ne nomme les versions que par identifiant : `WorkflowEditor.merged` les nomme depuis les listes lues pour la feuille (`GET /v1/ciXcodeVersions`, une fois par session, et `GET /v1/ciXcodeVersions/{id}/macOsVersions` par version choisie), puis `CIWorkflow.adopt` pose la réponse sur le workflow connu sans toucher aux actions ni aux conditions. `BuildStore.applyWorkflow` garde la réponse contre une synchro commencée avant, comme `setWorkflowEnabled`. Déclencheurs, actions, variables d'environnement et `DELETE` ne sont jamais exposés. Le rôle de clé requis n'est pas documenté : l'essai réel est fait par l'utilisateur, les agents n'envoient pas cette écriture.

**Version d'Xcode dépassée** (XCO-89) : la synchro inclut `xcodeVersion` avec les workflows (`CIWorkflow.xcodeVersion`, le numéro nu) et lit `GET /v1/ciXcodeVersions` une fois par jour (`BuildSnapshot.xcodeVersions`, même rythme que les icônes, nouvel essai dans l'heure après un échec). Apple ne marque ni la dernière ni les bêtas : `XcodeVersionCheck` (`CLI/`, pur) prend la plus haute `version` dont le `name` ne dit pas « beta », « Release Candidate » ou « RC », compare par composants, et ne signale qu'une version strictement inférieure (un workflow réglé sur « dernière version » ne se distingue pas de l'un figé sur la version du moment). Bandeau en tête de la fiche du workflow (« Modifier… » quand la retouche existe, sinon « Ouvrir dans App Store Connect »), point `arrow.up.circle` dans la barre latérale, `latestXcodeVersion` dans `cumulus workflows`.

**Builds planifiés** (XCO-88) : la synchro demande `scheduledStartCondition` avec les workflows (aucune requête de plus) ; `CIStartConditions.schedule` (`CISchedule` : fréquence, jours au sens de `Calendar`, heure, minute, fuseau, branches) vit dans l'instantané. `ScheduleForecast` (`CLI/`, pur) calcule le prochain passage dans le fuseau du déclencheur (`Calendar.nextDate`), le nombre de passages d'ici la fin du cycle et leur coût d'après `WorkflowUsage.averageMinutes` ; la section « À venir » de la Vue d'ensemble les liste (workflows actifs seulement) et dit le total comme une estimation ; rien sans forfait. `cumulus workflows` expose `nextScheduledRun`.

**Tendances d'un workflow** (XCO-87) : sous les tests de la fiche d'un workflow, `WorkflowTrendsSection` montre la durée médiane, l'attente médiane en file (`startedDate − createdDate`) et le taux de réussite des 30 derniers builds terminés (annulés et ignorés exclus), avec la dérive des 10 plus récents par rapport aux précédents (rien sous 6 builds, « stable » sous ±15 %), et un histogramme des durées, échecs en rouge, dont chaque barre ouvre le build. Tout est calculé par `WorkflowTrends` (`CLI/`, pur, partagé avec `cumulus workflows` qui l'expose en `trends`) depuis l'instantané : aucune requête, redessiné à la synchro seulement.

**Branches et pull requests** (XCO-86) : l'entrée « Branches et pull requests » de la barre latérale (`SidebarSelection.references`, adresse `cumulus://references`) remplace la colonne des builds par `ReferencesListView` : une ligne par référence que les builds du cache nomment, avec son dernier build (`ReferencesModel`, pur ; le build d'une PR compte pour la PR, jamais pour sa branche). **Une référence appartient à son app** (XCO-112, choix de l'utilisateur le 12/10/2026) : son identité est `AppReference` (produit + `ReferenceKey`), deux apps qui construisent « main » ont chacune leur ligne, et la liste ouverte ne contient que les builds de cette app. Un clic pose `NavigationModel.referenceScope` et la colonne redevient la liste des builds, limitée à cette référence (`BuildListScope.reference`), avec un retour en tête. Une PR fermée reste dans le cache : `ReferencesStore` lit la liste des PR ouvertes du dépôt (`GET /v1/scmRepositories/{id}/pullRequests`) à l'ouverture de la vue puis toutes les 5 min au plus, pas sous `SyncSchedule.criticalRemaining` ; tant qu'elle n'a pas pu être lue, toutes les PR du cache s'affichent et la vue le dit. Les PR ouvertes se rangent par dépôt (`OpenPullRequests`) : un numéro se cherche dans le dépôt du workflow qui a construit, puisque deux dépôts peuvent porter le même. `cumulus builds --branch <nom>` et `--pr <numéro>` (et `branch`, `pull_request` de `list_builds`) filtrent de même.

**Première récupération** (XCO-83) : `WindowContentState` décide de ce que la fenêtre montre avant d'avoir des colonnes à remplir. Tant que l'app n'a **rien du tout** à montrer (aucun compte n'a de contenu, `BuildSnapshot.hasContent`), un écran plein avec indicateur de progression dit l'étape en cours ; si cette première synchro échoue, l'erreur avec « Réessayer ». Dès qu'un compte a des données, la première récupération d'un compte ajouté ensuite ne bloque plus rien : les colonnes restent, et sa progression passe en carte nommée au pied de la barre latérale (`SyncActivity.background`). « Cumulus n'est pas configuré » n'apparaît qu'une fois la clé cherchée et absente (`BuildStore.hasAttemptedSync`), plus pendant le démarrage.

**Mesure au premier chargement** : les résultats de tests par appareil arrivent par lots de 12 actions, du build le plus récent au plus ancien, un lot par synchro, soit toutes les 30 s (`BuildSynchronizer`). Tant que le cycle en a en attente, `UsageSummary.measurement.isMeasuring` est vrai et le menu n'affiche aucun chiffre qui dépendrait d'eux. Une action refusée trois fois par Apple est abandonnée (`BuildSnapshot.testResultAttempts`) ; un 429 ne coûte aucune tentative.

**Localisation** (XCO-21 à 23) : langue source anglaise, `Localizable.xcstrings` traduit en français. `xcodebuild` ne met pas à jour le catalogue source (seul Xcode le fait) : après l'ajout d'une chaîne, le resynchroniser avec `xcrun xcstringstool sync xcode-cloud-companion/Localizable.xcstrings --stringsdata <DerivedData>/…/Objects-normal/arm64/*.stringsdata`, puis traduire la nouvelle entrée (le test `FrenchLocalizationTests` échoue sinon). Le schéma fixe la langue des tests à l'anglais. Un `NSMenuItem` n'affiche aucune `image` dans ce menu : voir les pièges ci-dessus.

Les tests s'exécutent **dans l'app** (`TEST_HOST`) : `AppDelegate` ne démarre ni la synchronisation ni la migration des comptes quand `XCTestConfigurationFilePath` est défini, pour ne jamais appeler l'API avec la vraie clé ni déplacer les vraies données pendant les tests.

## 2. Workflow

### Branches

Le travail se fait sur une **branche de feature** au format `claude/<description>-<hash>` (ou `codex/…` pour Codex), créée **dans le dossier principal** du dépôt, pas dans un `git worktree`. **Ne jamais commiter directement sur `main`**, ne pas pousser la branche vers `origin` ni ouvrir de PR de soi-même : le travail reste **local** pendant tout le statut **In Review**, pour que l'utilisateur le teste sur sa machine.

Un ticket demandé en cours de session se développe **sur la branche en cours**, avec son propre commit. Ne changer de branche que si l'utilisateur le demande.

Une fois l'utilisateur revenu avec sa validation (ticket → **Done**, cf. § Tickets) : squash-merge de la branche dans `main` en local, puis suppression de la branche.

```bash
git checkout main
git merge --squash claude/<branche>
git commit -m "XCO-12: …"          # ou « projet: <nom du projet> », cf. § Style de commits
git branch -D claude/<branche>     # -D : après un squash, git ne voit pas la branche comme fusionnée
```

Plusieurs sessions peuvent tourner en parallèle dans ce dossier :
- toujours stager des **chemins explicites** (`git add <chemins>`), jamais `git add -A`, `git add .` ni `git commit -a` ;
- `git status --short` et `git branch --show-current` juste avant chaque commit ;
- jamais de `git reset --hard`, `git stash` ni `git checkout -- .` global.

Les reformatages massifs faits par Xcode (imports, accolades) se laissent tels quels.

### Style de commits

Titres courts **en français, à l'indicatif, qui disent l'effet produit** plutôt que le fichier touché (« Le menu montre les heures consommées sur le cycle », « Un build échoué s'affiche en rouge dans le sous-menu de son app »). Préfixe :

- **un ticket** : son identifiant, sans type ni parenthèses — `XCO-12: Le menu montre les heures consommées sur le cycle`. Plusieurs tickets dans un même commit : le préfixe une seule fois, puis les numéros séparés par des tirets — `XCO-3-4: …` (chaque numéro est cité, ce n'est pas un intervalle) ;
- **un projet Linear entier, squash-mergé d'un coup** : `projet: <nom du projet>`. Le corps du commit liste alors les tickets, un par ligne (`XCO-12 Le menu montre les heures consommées sur le cycle`), puisque le squash efface les commits par ticket ;
- **aucun ticket** (retouche d'AGENTS.md, rapports) : le titre seul, sans préfixe.

### Granularité des commits

Sur une branche qui traite plusieurs tickets, faire **un commit distinct par ticket** dès que son implémentation est cohérente (tests ciblés inclus). Ne pas accumuler les changements jusqu'à la fin du lot, et ne pas mélanger les fichiers de tickets indépendants dans un même commit. Si un fichier partagé est modifié par plusieurs tickets, séparer ses hunks dans l'index.

- **In Review** — implémentation terminée, en attente de validation utilisateur.
- **Done** — validé par l'utilisateur.
- **Canceled** — abandonné (garder la trace, ne pas supprimer).
- **Duplicate** — doublon d'un autre ticket.

## 3. Conventions de code

- **Concurrence Swift 6 stricte, isolation par défaut `MainActor`** (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, `SWIFT_APPROACHABLE_CONCURRENCY = YES`). Chaque type reçoit une isolation choisie, pas subie :
  - **`MainActor` seulement pour ce qui touche l'interface** : vues SwiftUI, `NSStatusItem` / `NSMenu`, état observé par les vues ;
  - **`nonisolated` pour tout le reste** : modèles de données (structs `Sendable`), décodage, calcul de l'usage, construction des requêtes, formatage. C'est le cas le plus fréquent ;
  - **un `actor` seulement s'il protège un état mutable partagé** (cache, jeton JWT en cours de validité) ;
  - **de l'asynchrone seulement quand c'est indispensable** (réseau, disque, trousseau). Une fonction de calcul reste synchrone ;
  - **pas de saut d'acteur inutile** : on ne fait pas d'aller-retour vers le `MainActor` pour une donnée qui peut se calculer ailleurs, et on ne passe à l'interface que le résultat final.
- **Économie de données** : ne demander à l'API que ce qui sert (`fields[…]`, `limit`, `include` ciblés), ne pas redemander ce qui est en cache, ne garder en mémoire que ce que l'interface affiche.
- **Pas de contournement** : ni `nonisolated(unsafe)`, ni `@unchecked Sendable`, ni `@preconcurrency import`. Chercher la vraie isolation ; si un contournement semble inévitable, le signaler et le justifier.
- **Ajout de fichiers** : le projet utilise des groupes synchronisés, un fichier créé dans `xcode-cloud-companion/` est pris en compte sans éditer `project.pbxproj`. Un fichier créé dans `CLI/` entre dans l'app et dans la commande `cumulus`.
- **Secrets** : la clé `.p8`, l'Issuer ID et le Key ID vivent dans le trousseau. Ne jamais les écrire dans le code, les logs, les tests ni les tickets.
- **Tests** : Swift Testing. Le calcul de l'usage (cycles, quota, rythme) et le décodage des réponses de l'API se testent avec des fixtures JSON, sans appel réseau.
- **Commentaires** : aucun par défaut. Seulement pour un *why* non évident (contrainte de l'API, invariant caché).
- **Pas d'emoji dans les fichiers source**, sauf demande explicite.
