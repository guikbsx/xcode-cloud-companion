# AGENTS.md — Guide des agents pour Cumulus

Ce document oriente les sessions d'agents (Claude Code, Codex) qui travaillent sur ce dépôt. Il décrit le produit, le workflow et les conventions. **Lis-le en premier.**

---

## 1. Vue d'ensemble

**Cumulus** (dépôt, target et équipe Linear : « Xcode Cloud Companion ») est une app macOS qui vit dans la barre des menus. Elle surveille la consommation Xcode Cloud d'un compte App Store Connect (heures de calcul utilisées par rapport au forfait) et liste les builds récents de chaque app.

| | |
|---|---|
| Plateforme | macOS 26.0+ (`MACOSX_DEPLOYMENT_TARGET = 26.0`, XCO-151 : aucune API propre à macOS 27 n'est utilisée ; descendre sous 26 demanderait une interface sans verre) |
| Langage | Swift, SwiftUI pour les vues, AppKit pour la structure du menu |
| Target / scheme | target `xcode-cloud-companion`, scheme `Cumulus` (produit : `Cumulus.app`, module `XcodeCloudCompanion`, bundle ID `com.guik.xcode-cloud-companion`) |
| Sandbox | Activé (garder la porte du Mac App Store ouverte) |
| Dépendances | Aucune |

### Source de données : API App Store Connect

- Authentification par jeton JWT ES256, signé avec une clé API `.p8` (Issuer ID + Key ID). La clé est stockée dans le trousseau, jamais en clair.
- Chemin des données : `GET /v1/ciProducts` → `GET /v1/ciProducts/{id}/buildRuns` → `GET /v1/ciBuildRuns/{id}/actions`. Aucun endpoint ne liste d'un coup tous les builds de l'équipe.
- `ciBuildRuns` et `ciBuildActions` exposent `startedDate`, `finishedDate`, `executionProgress` (`PENDING`, `RUNNING`, `COMPLETE`) et `completionStatus` (`SUCCEEDED`, `FAILED`, `ERRORED`, `CANCELED`, `SKIPPED`). Les actions ont aussi `actionType` (`BUILD`, `ANALYZE`, `TEST`, `ARCHIVE`) et les builds `startReason`.
- ⚠️ **Aucun endpoint n'expose la consommation ni le quota Xcode Cloud** (vérifié dans la doc Apple le 09/10/2026). La consommation affichée est donc une **estimation** : la somme des durées des actions (elles tournent en parallèle sur des machines distinctes). Le forfait et le jour de réinitialisation sont saisis par l'utilisateur. Toujours présenter le chiffre comme une estimation.
- **Mesuré sur le vrai compte le 13/10/2026** (XCO-51, lecture seule) : `X-Rate-Limit` vaut `user-hour-lim:3600;user-hour-rem:…;`. `GET /v1/ciProducts` **ne pagine pas** : `limit` tronque la liste sans `links.next`, et `meta.paging.total` vaut alors le nombre rendu, pas le vrai total ; l'app demande 200, le maximum. Les listes de builds paginent : `links.next` reprend le chemin et la requête d'origine avec un `cursor` (264 caractères), que `meta.paging.nextCursor` répète. `sourceCommit` est rempli aussi hors pull request. Le `downloadUrl` d'un artefact pointe sur `cvws.icloud-content.com`, vaut environ 15 minutes (paramètre `e`, une date Unix) et se télécharge sans `Authorization` ; le jeton de l'API ne lui est jamais envoyé.
- Un build `COMPLETE` ne change plus : il se met en cache et ne se redemande pas. Seuls les builds en cours ou récents se rafraîchissent, pour ménager la limite de requêtes de l'API.

### Interface : un vrai menu natif

Le modèle est CodexBar : un `NSStatusItem` + `NSMenu`, dont certaines lignes sont des vues SwiftUI hébergées (barres de progression, chiffres, histogramme). Le reste, ce sont des `NSMenuItem` standards (sous-menus, surlignage, navigation clavier). Ne pas remplacer par un popover ni par `MenuBarExtra(.window)`.

### Architecture

**Cycle de vie AppKit**, pas d'`App` SwiftUI : `AppDelegate` porte `@main` et lance `NSApplication`. Depuis macOS 14, la scène `Settings` de SwiftUI ne s'ouvre pas depuis un `NSMenu` ; les Réglages sont une `NSWindow` qui héberge une vue SwiftUI. `MainMenu` est un menu complet (Cumulus, Fichier, Édition, Présentation, Fenêtre, Aide) : invisible tant que l'app est `.accessory`, il porte quand même ⌘, ⌘Q ⌘W ⌘0 et le menu Édition, sans lequel ⌘V ne marche pas dans les champs. La fenêtre principale est une `NSWindow` (une scène SwiftUI `Window` ne s'ouvre pas depuis un `NSMenu`), comme les Réglages ; un clic sur un build du menu l'ouvre sur ce build.

**Plusieurs comptes** (XCO-71, XCO-77 ; sans Cumulus Pro, seul le premier est suivi, voir « Comptes en pause ») : l'app suit autant de comptes App Store Connect (équipes) qu'on lui donne de clés. **Tous se synchronisent en permanence**, chacun avec sa clé et donc son propre budget de requêtes ; **un seul est sélectionné**, et c'est lui que montrent le menu, la fenêtre et la commande `cumulus`. **Zéro compte est un état normal** (installation neuve, dernier compte supprimé) : le menu ne propose qu'« Ajouter un compte… », la fenêtre son état vide, `cumulus` répond `NO_CACHE`. Un compte n'existe qu'une fois sa clé acceptée par Apple (`NewAccountModel` teste, puis `AccountsModel.add` crée le compte et range la clé) : il n'y a jamais de compte sans clé, et le lancement efface ceux qu'une version précédente avait créés sans clé ni cache. Un compte, c'est une `AccountSession` : son `SettingsModel` (clé et forfait), son `BuildStore`, son `UsageStore`, son `BuildExtrasStore` et, pour la fenêtre, ses `AccountWindowStores`. Rien n'est partagé entre deux comptes :
- **trousseau** : même service, `kSecAttrAccount` = identifiant du compte. Le premier compte s'appelle `default` (`AccountRegistry.firstAccountID`), la valeur que portait l'élément d'avant les comptes. L'adresse du webhook d'un compte (XCO-147) est un second élément, sous un autre service (`KeychainWebhookAddressStore`), avec la même règle de compte ;
- **fichiers** : `Accounts/<id>/` dans le conteneur de groupe et `Caches/Accounts/<id>/` (`AccountPaths`). Les valeurs par défaut des stores (`BuildCacheStore()`, `LogCache()`…) pointent sur le premier compte : l'app passe toujours les chemins du compte ;
- **préférences** : `account.<id>.<clé>` (`AccountDefaults.names` : forfait, date de réinitialisation, accès de la clé, palette, état des alertes de forfait, builds bloqués déjà signalés, builds de rupture déjà signalés, événements envoyés au webhook, état des alertes de forfait du webhook). Une préférence par compte s'ajoute à cette liste, sinon la suppression d'un compte la laisse derrière elle. Les épinglés, les apps muettes et les réglages de notifications restent communs : ils sont indexés par des identifiants d'Apple, uniques d'un compte à l'autre.

Le registre (`Accounts.json` à la racine du conteneur de groupe : noms, identifiants, compte sélectionné ; jamais l'Issuer ID) est écrit par l'app et lu par `cumulus`. Au premier lancement sans registre, `AccountMigration` fait de l'installation existante le premier compte (fichiers déplacés, préférences reprises), seulement si elle avait une clé ou un cache. `AccountsModel.start()` est appelé **avant** que la fenêtre puisse s'ouvrir, et tout ce qui lit un cache attend `whenReady()` : un cache lu avant son déplacement serait pris pour vide et tout serait redemandé à Apple. Supprimer un compte (`AccountSession.erase`, la seule suppression qui existe, le dernier compte compris) retire sa clé, puis attend la fin d'une synchro en cours (`BuildStore.retire`) avant d'effacer ses dossiers ; si le trousseau refuse, rien n'est touché. **Les Réglages sont une fenêtre à barre latérale** (XCO-97), à la manière de Réglages Système : `SettingsWindowController` héberge `SettingsRootView`, un `NavigationSplitView`. La barre latérale liste Général, Notifications et Agents, puis chaque compte avec le point de son état (`AccountHealth`), puis « Ajouter un compte… » : un compte est une destination (`SettingsDestination`), plus une liste dans un onglet. `SettingsNavigationModel` tient le volet affiché, mémorisé par son nom sous `settings.selectedTabName` (les noms des anciens onglets sont repris) ; la fenêtre s'ouvre sur un compte tant qu'il n'y en a aucun ou que l'un d'eux réclame sa clé ou sa date. La sélection d'un compte (`AccountsSettingsModel`) est propre aux Réglages et ne change jamais le compte affiché par le menu. Le volet d'un compte (`AccountsSettingsView` puis `AccountDetailView`) porte le nom du compte en titre, son état en sous-titre et « Tester la connexion » dans la barre d'outils. Sa fiche tient en groupes courts (XCO-98) : Compte (nom, clé, accès, apps trouvées), Forfait, Minutes facturées, Dépôts locaux, puis la suppression ; un bandeau ne s'ajoute que pour une clé refusée ou un test en cours. Les guides ne s'affichent plus d'office : celui du forfait tant que la date manque, les deux derrière « Où trouver la clé et la date de réinitialisation ? » ; un compte sans clé ne montre que la saisie de la clé. La saisie d'une clé (nouveau compte, ou compte dont la clé manque) est en deux colonnes (`KeyEntryColumns`, XCO-99) : le formulaire à gauche, le guide en quatre étapes à droite, qui reste en vue ; sous 640 pt de large, le guide passe sous le formulaire. Les minutes facturées (exports importés) se lisent dans le détail du compte : il n'y a plus d'onglet Usage (XCO-78) ; un export choisi depuis le détail d'un compte va à ce compte quand ses apps ne disent rien. La fenêtre s'ouvre à 900 × 720 et garde la taille qu'on lui donne tant qu'elle reste ouverte. **Son minimum (700 × 460) est tenu par le délégué** (`windowWillResize`) : le contenu SwiftUI efface un `contentMinSize` posé sur la fenêtre (vérifié le 12/10/2026). En Debug, `XCC_SETTINGS=general|notifications|agents|accounts` ouvre les Réglages sur ce volet au lancement. Le volet Général (XCO-102) s'ouvre sur l'icône de l'app, sa version lue dans le bundle et la fraîcheur des builds du compte affiché, puis deux groupes : Démarrage et fenêtre, Langue. Changer de compte vide la sélection de la fenêtre (`NavigationModel.accountDidChange`) ; ouvrir un build d'un autre compte (menu, bannière, adresse, socket) sélectionne d'abord le compte qui le détient (`AccountsModel.owner(ofBuild:)`). Le sélecteur en tête du menu (`AccountSwitcherControl`, absent avec un seul compte) est dessiné en SwiftUI mais prend ses clics en AppKit (`mouseUp`), et le menu se reconstruit sous lui sans se fermer. Le clavier n'atteint pas une vue de menu : ⌘1 à ⌘9 sont portés par des items masqués (`allowsKeyEquivalentWhenHidden`, XCO-76), et le menu se ferme comme sur tout raccourci ; VoiceOver lit un groupe de boutons radio (`AccountSwitcherElement`, un par compte, posé là où il est dessiné), le dessin SwiftUI lui étant caché. La pastille de la barre parle pour tous les comptes : un build en cours quelque part, sinon un échec quelque part. Un export d'usage ne nomme pas son équipe : `UsageImportRouting` l'envoie au compte dont il liste les apps ; s'il n'en liste aucune connue, il n'est pas importé tout seul, et va au compte affiché quand l'utilisateur le choisit à la main. Les tests passent par `TestAccounts` (dossier temporaire, trousseau en mémoire) ; sous tests, `AppDelegate` ne migre rien.

**Cible `cumulus`** (XCO-57, vérifié le 10/10/2026) : un outil en ligne de commande (bundle ID `com.guik.xcode-cloud-companion.cli`, Info.plist embarqué dans le binaire), signé avec **sa propre** sandbox et l'app group `4HYT2U85R2.com.guik.cumulus` (`Config/cumulus-cli.entitlements` ; l'app porte le même groupe par `Config/Cumulus.entitlements`). Un helper signé « inherit » serait tué dès qu'on le lance depuis un terminal. Il ne lit ni le trousseau ni le réseau : seulement ce que l'app écrit dans le conteneur de groupe (`SharedContainer.applicationSupport` : `Accounts.json`, puis par compte, dans `Accounts/<id>/`, `BuildCache.json`, `UsageLedger.json`, `UsagePlan.json`, `BuildDetails/`, `WorkflowDetails/`, `TestFlight.json`, `TestFlightGroups.json`). `CacheMigration` y déplace une fois les caches d'avant. Le forfait vit dans les préférences de l'app, hors de portée du CLI : le `SettingsModel` de chaque compte en tient une copie par `SharedPlanStore`. Les fichiers de l'app que le CLI compile sont listés un par un dans `project.pbxproj` (`PBXFileSystemSynchronizedBuildFileExceptionSet` de la cible `cumulus`) : un nouveau fichier partagé s'y ajoute à la main ; aucun fichier qui importe AppKit ou SwiftUI. XCO-177 y a ajouté `TestFlight/TestFlightModels.swift` et `TestFlight/TestFlightFiles.swift` (les fichiers `TestFlight.json` et `TestFlightGroups.json`, leurs types et `nilIfBlank`) ; `TestFlightApp`, qui lit `shipsToTestFlight`, vit à part dans `TestFlightApp.swift`.

**Contrat de la commande `cumulus`** (XCO-58) : `status`, `accounts`, `apps`, `builds`, `build <App#42 | id>`, `workflows`, `usage`, `open`, `refresh [--wait]`, `run <workflow>` (XCO-61), `testflight <App#42 | id>`, `testflight give …` et `testflight expire …` (XCO-177). JSON dans un tube, tableau sur un terminal (`--json` / `--table`). Chaque commande répond pour le compte sélectionné dans l'app, ou pour celui que nomme `--account <nom>` (`CLIAccountScope` ; `accounts` les liste). Enveloppe `{ data, meta }` ; `meta.lastSuccessfulSync` dit l'âge du cache, `meta.appRunning` si l'app répond sur son socket, `meta.isEstimate` signale des minutes estimées, et `meta.account` nomme le compte de la réponse. Erreurs sur stderr (`{ error: { code, message, suggestions } }`), codes de sortie 0, 1, 2 (usage), 3 (pas de cache ou pas de clé), 4 (app injoignable), 5 (introuvable ou ambigu), 6 (délai dépassé), 7 (clé en lecture seule ou 403, `run`), 8 (plafond de lancements ou limite d'Apple, `run`), 9 (`PRO_REQUIRED` : Cumulus Pro n'est pas actif, toute commande sauf `status`) ; `testflight give` et `expire` reprennent les codes 7 (clé en lecture seule ou 403), 8 (plafond de dix écritures TestFlight ou limite d'Apple) et 1 (`REFUSED`) de `run`. Les noms de propriétés des types de `CLI/CLIModels.swift` **sont** les clés JSON publiques : en renommer une casse les agents, et `CLICommandTests` le signale. Sortie en anglais, hors catalogue de traduction. `CLIQueryRunner` répond à une `CLIQuery` ; la ligne de commande et le serveur MCP passent tous deux par lui.

**Socket entre l'app et `cumulus`** (XCO-59, vérifié le 10/10/2026) : l'app écoute un socket Unix `ipc.sock` à la racine du conteneur de groupe, le seul endroit où la sandbox en permet un (`IPCSocketServer`, POSIX + Dispatch ; le chemin tient en 103 octets, d'où la racine et un identifiant de groupe court). Un objet JSON par ligne dans chaque sens (`CLI/IPC/`) : `ping`, `refresh { wait }`, `open { buildRunID }`, `loadDetails { buildRunID }`. `testFlightLoad { buildRunID }`, `testFlightGive` et `testFlightExpire` (XCO-177, voir « TestFlight depuis un agent »). `ping`, `refresh`, `launch`, `testFlightGive` et `testFlightExpire` acceptent un `accountID` (le compte sélectionné sinon) ; `open` et `loadDetails` trouvent seuls le compte du build. Seules `launch` (XCO-61, voir « Lancer depuis un agent ») et `testFlightGive` / `testFlightExpire` (XCO-177) écrivent chez Apple. `AppIPCService` refuse une synchro de moins de 30 s (`recent`) et n'en lance pas une seconde (`syncing`). `loadDetails` charge les problèmes, tests et artefacts d'un build terminé comme le fait sa fiche : c'est ce qui permet à `cumulus build` de répondre sur un build jamais ouvert dans la fenêtre. Un socket accepté hérite du mode non bloquant de l'écoute sur macOS : il est remis en bloquant. Les attentes sur socket se font sur une file Dispatch, jamais sur le pool de concurrence Swift. Une seconde instance de l'app laisse le socket de la première ; le serveur ne démarre pas sous tests.

**Serveur MCP** (XCO-60, vérifié avec Claude Code le 10/10/2026) : `cumulus mcp` parle Model Context Protocol sur stdio, écrit à la main dans `CLI/MCP/` (JSON-RPC 2.0, un message par ligne ; `initialize`, `ping`, `tools/list`, `tools/call` ; versions 2025-03-26, 2025-06-18 et 2025-11-25). Douze outils, chacun rendant le JSON de la commande correspondante en texte et en `structuredContent` : `get_status`, `list_apps`, `list_builds`, `get_build`, `list_workflows`, `get_usage`, `refresh`, `start_build`, `get_testflight`, `give_testflight_build`, `expire_testflight_build`, `list_accounts`. Tous sauf le dernier prennent `account`, l'équivalent de `--account` (`MCPTool.takesAccount`). Une erreur métier est un résultat `isError: true` que le modèle lit, jamais une erreur JSON-RPC. Rien d'autre que le protocole ne s'écrit sur stdout ; `--verbose` journalise sur stderr. Un outil s'ajoute dans `MCPTools.all`, avec sa description écrite pour un agent ; `start_build` est le seul qui lance un build (`idempotentHint: false`), aux conditions ci-dessous ; `give_testflight_build` et `expire_testflight_build` écrivent chez Apple (`idempotentHint: false`, `destructiveHint: true` pour l'expiration seule), aux conditions de « TestFlight depuis un agent » (`MCPTool.destructive`).

**Cumulus Pro** (XCO-132, XCO-135, 13/10/2026) : l'app est gratuite pour un compte ; Cumulus Pro se paie 19,99 € par an avec un mois d'essai, ou 59,99 € à vie, par StoreKit 2, sans serveur ni dépendance. Deux produits (`ProProduct`) : `com.guik.cumulus.pro.yearly`, dans le groupe d'abonnements « Cumulus Pro », et `com.guik.cumulus.pro.lifetime`, non consommable ; un identifiant de produit ne prend pas de tiret et ne se change jamais. `ProStore` (`Pro/`, créé par `AppDelegate`) est **le seul endroit qui dit si Pro est ouvert** : vues et modèles ne posent que `allows(_:)`, avec un cas de `ProFeature`, la liste fermée des fonctions Pro (la répartition décidée est dans XCO-132 ; les verrous sont décrits plus bas : « Verrous de Cumulus Pro », « Commande et serveur MCP sous Pro », « Comptes en pause »). L'état (`ProEntitlement` : gratuit, essai, abonné, à vie, expiré) est un calcul pur sur les transactions (`ProEntitlement.resolve`) : une transaction que StoreKit n'a pas vérifiée n'ouvre rien, l'achat à vie l'emporte sur tout abonnement, la période de grâce et la relance de facturation gardent Pro ouvert, un abonnement fini ou remboursé donne « expiré » et non « gratuit ». **Rien n'est écrit dans les préférences** : StoreKit garde les transactions vérifiées sur le Mac, l'état est donc connu hors ligne. `StoreKitProSource` lit `Transaction.currentEntitlements` (et `Transaction.latest` pour un abonnement fini, qui n'y figure plus), suit `Transaction.updates` et `Product.SubscriptionInfo.Status.updates` ; `ProStore` relit aussi juste après la fin d'une période, qui n'amène pas toujours de transaction. Sous tests, `AppDelegate` ne démarre pas l'écoute. En Debug, `XCC_PRO=0|1|trial|lifetime|expired` fige l'état sans rien lire. `xcode-cloud-companionTests/Cumulus.storekit` décrit les deux produits : copié dans le bundle de tests pour `SKTestSession`, et branché sur le lancement du scheme `Cumulus` (vérifié par l'utilisateur le 13/10/2026 : le chemin écrit dans le scheme part du dossier au-dessus de `xcschemes`, soit `../../xcode-cloud-companionTests/Cumulus.storekit` ; avec un `../` de trop, Xcode ne dit rien et l'app passe par le bac à sable de l'App Store, prix en dollars et dialogues « Environment: Sandbox »). **Piège des tests d'achat** (vérifié le 13/10/2026) : dans un test hébergé par l'app, ce que la session fait de son côté (`buyProduct`, `expireSubscription`, `refundTransaction`) n'arrive pas à StoreKit dans le processus : aucun événement `Transaction.updates`, et les requêtes gardent leur première réponse. Un test achète donc par `ProStore.purchase` (dialogues coupés) et appelle `ProStore.restore()` après un geste de la session. **Chaque test d'achat vide ses transactions en sortant** (`defer { session.clearTransactions() }`) : un achat laissé dans le magasin local est lu comme vrai par une app de Debug lancée ensuite, hors de Xcode compris, qui se croit alors Pro et l'écrit dans `Pro.json` (vu le 13/10/2026). La cible de tests passe `-Xcc -iframework` sur les frameworks de la plateforme : sans cela, un en-tête de StoreKitTest émet un avertissement de dépréciation à chaque compilation.

**Feuille d'achat** (XCO-136, option A des maquettes retenue le 13/10/2026) : `ProPurchasePresenter` accroche à une fenêtre une feuille AppKit qui héberge `ProPurchaseView`. **Elle ne s'ouvre jamais d'elle-même** : aujourd'hui par Cumulus › « Cumulus Pro… » (`AppDelegate.openCumulusPro`, qui ouvre d'abord la fenêtre principale), ensuite par une fonction verrouillée ou les Réglages. `ProPurchaseModel` tient le produit choisi et la réponse de l'App Store : les prix sont ceux de `Product.displayPrice`, jamais écrits dans le code ; l'essai n'est proposé qu'à qui y a droit (`isEligibleForIntroOffer`), sinon le bouton dit le prix ; sans produit, la feuille le dit et ne montre aucun bouton d'achat ; un achat réussi ferme la feuille, un achat annulé la laisse sans message, un achat en attente d'approbation le dit sans ouvrir Pro. Qui a déjà Pro voit son état, pas une offre. Les mots sont dans `ProPurchaseText`, `ProEntitlementText` (un état de Pro, repris par les Réglages) et `ProBenefit` (le bénéfice d'où l'on vient se lit en premier ; un test échoue si une `ProFeature` n'appartient à aucun bénéfice). Conditions d'utilisation : l'EULA standard d'Apple ; confidentialité : `cumulus.guik.io/privacy/` (`ProLinks`). **Piège** (plantage de l'hôte de tests vu le 13/10/2026) : une `NSWindow` créée en code est libérée par son propre `close` ; poser `isReleasedWhenClosed = false`, sinon Swift la libère une seconde fois. Dans un rendu hors écran, le bouton principal sort gris : la fenêtre n'est pas active.

**Volet Cumulus Pro des Réglages** (XCO-137) : une destination de plus de la barre latérale (`SettingsDestination.pro`, `SettingsNavigationModel.Pane.pro`, mémorisée comme les autres ; `XCC_SETTINGS=pro` l'ouvre en Debug). `ProSettingsView` dit l'état avec les mots de `ProEntitlementText` et propose ce que l'état permet (`ProSettingsAction.actions(for:)`) : sans Pro ou après expiration, « Découvrir… » ou « Reprendre Cumulus Pro… » (qui ouvre la feuille d'achat sur la fenêtre des Réglages), « Restaurer les achats » et « Utiliser un code… » (la feuille d'App Store, `offerCodeRedemption`, posée sur le volet et non dans une section) ; en essai ou abonné, « Gérer l'abonnement… », qui ouvre `apps.apple.com/account/subscriptions` (macOS n'a pas de feuille de gestion) ; à vie, rien. **Le volet ne montre jamais de prix** : c'est la feuille qui vend. Les comptes en trop à la fin d'un abonnement ne sont pas encore traités (XCO-138).

**Verrous de Cumulus Pro** (XCO-139, 13/10/2026) : chaque verrou est un cas de `ProFeature`, et `ProStore.allows` est la seule réponse. **Pro** : « Ce qui a cassé » (`regressions`), « En bref » et groupes suggérés (`failureInsight`, avec Apple Intelligence et le réglage), « Extrait du journal » (`logExcerpt`, XCO-161), tests instables et lents, et l'histoire d'un test (`testHealth`), tendances (`workflowTrends`), « Pourquoi un workflow coûte » (`workflowCostBreakdown`), « À venir » (`upcomingBuilds`), vue d'ensemble d'une app (`appOverview`), builds plus anciens (`olderBuilds`), « Ouvrir dans Xcode » depuis le clone local (`openInXcode`), pause et retouche d'un workflow (`pauseWorkflow`, `editWorkflow`), alerte à 75 % et alerte de rythme (`earlyUsageAlerts`), build bloqué (`stuckBuildAlert`), bannière « a ralenti » (`slowdownAlert`, XCO-163), alertes vers un webhook (`webhookAlerts`, XCO-147), suivi de TestFlight : carte, frise et bannières (`testFlightTracking`, XCO-164) ; donner un build TestFlight à des groupes de testeurs (`testFlightDistribution`, XCO-175, voir « Écriture : distribuer un build TestFlight ») ; commande et serveur MCP (`commandLine`, `mcpServer`, voir « Commande et serveur MCP sous Pro »), second compte (`multipleAccounts`, voir « Comptes en pause »). **Gratuit** : un compte, la jauge et la consommation (toujours dites comme une estimation), les builds et leur fiche, journaux et artefacts, lancer et relancer un build, copier un build en échec pour une IA, branches et pull requests, notifications de fin de build, alerte à 90 %, temps restant du build en cours dans la barre des menus, incident Apple sur Xcode Cloud (XCO-162), widgets, Siri et Raccourcis. La fenêtre reçoit un `ProAccess` (`Pro/ProAccess.swift`, `@Observable`, posé par `MainWindowController` avec `.environment`, lu par `@Environment(ProAccess.self) private var access: ProAccess?`) : sans lui (tests, aperçus) tout est ouvert, et l'état suit `ProStore` sans relancer ni rouvrir la fenêtre. Une **section** verrouillée est remplacée par `ProLockedCard` (nom, une phrase de `ProFeatureText`, « Découvrir Pro » qui ouvre la feuille d'achat sur ce bénéfice) ; la vue d'ensemble d'une app, qui est un écran entier, l'est par une page entière (`AppOverviewLockedPage` : l'icône et le nom de l'app, ce que l'écran montre en quatre cartes, le bouton ; demande de l'utilisateur le 13/10/2026, une carte seule dans la colonne faisait vide) ; un **bouton** verrouillé (pause, « Modifier… », builds plus anciens, « Ouvrir dans Xcode ») ouvre la feuille au lieu d'agir. La carte prend la place du groupe dans le `Layout` de la fiche, sous un `Group` qui garde son emplacement : les autres groupes ne changent pas d'identité. **Le verrou est aussi dans les stores** : `AccountsModel.pro` donne le `ProStore` à chaque `AccountSession`, et `AccountWindowStores` passe `allowed:` à `OlderBuildsStore`, `WorkflowPauser`, `WorkflowEditor` et `WorkflowTestsModel`, qui ne lisent ni n'envoient rien quand il dit non (les deux écritures répondent `ProFeatureText.required`). « Ce qui a cassé » et la vue d'ensemble d'une app passent par des stores que les fonctions gratuites partagent (`BuildExtrasStore`, `WorkflowDetailStore`) : là, c'est l'absence de la vue et de ses `.task` qui garantit qu'aucune requête ne part. `NotificationCoordinator(pro:)` ne cherche pas de build bloqué sans Pro (il n'est donc pas noté comme déjà signalé) et coupe le seuil de 75 % et le rythme avant `UsageAlertPlanner` ; Réglages › Notifications garde ces réglages visibles, grisés, avec la raison, et leur valeur est conservée. Le menu de la barre ne porte aucun rappel de Pro. Une fonction Pro nouvelle s'ajoute à `ProFeature`, à `ProFeatureText` (ses `switch` le réclament) et à `ProBenefit.features` (un test le réclame).

**Commande et serveur MCP sous Pro** (XCO-140, 13/10/2026) : la commande ne voit ni StoreKit ni les préférences de l'app. L'app écrit donc `Pro.json` à la racine du conteneur de groupe, à côté d'`Accounts.json` (`ProStatusStore`, `CLI/ProStatus.swift` : `isActive` et la date d'écriture), au lancement et après chaque lecture des transactions (`ProStore.onRead`, branché par `AppDelegate`), seulement quand la réponse change. **Un état figé par `XCC_PRO` n'écrit rien** : une instance de Debug partage le conteneur de l'app installée et verrouillerait sa commande. Rien sous tests. `ProGate.refusal(in:)` est la seule question posée : sans Pro, `CumulusCLI.run` refuse toute commande dont `CLICommand.needsPro` est vrai (tout sauf `status`, `help`, `version`, l'emplacement du cache, et `mcp` qui démarre toujours) avec `PRO_REQUIRED`, code de sortie 9, dans l'enveloppe d'erreur habituelle ; le serveur MCP répond à `initialize` et `tools/list` et rend ce refus à chaque `tools/call`, en résultat `isError: true` (hypothèse validée par l'utilisateur : le serveur reste enregistrable sans Pro). Fichier absent ou illisible : pas de Pro, et la suggestion est d'ouvrir l'app. **Le verrou n'est pas dans `CLIQueryRunner`** : les App Intents et les widgets, gratuits, passent par lui. Le fichier se modifie à la main, c'est assumé : seule la lecture du cache peut être forcée, car `AgentLaunchService.launch` redemande au `ProStore` de l'app (`IPCLaunchReason.proRequired`, même code 9). Sans Pro, Réglages › Agents ouvre sur un bandeau qui le dit et mène à la feuille d'achat ; le volet reste utilisable et aucun lien installé n'est retiré. Le skill documente `PRO_REQUIRED`. `CLIFixture.environment(pro:)` écrit le fichier pour les tests (actif par défaut, `nil` pour l'absence).

**Comptes en pause** (XCO-138, décisions de l'utilisateur le 13/10/2026) : un premier compte est gratuit, un de plus demande Pro (`AccountsModel.canAddAccount`). Sans Pro et avec un compte, « Ajouter un compte… » ouvre la feuille d'achat avant toute saisie de clé (ligne de la barre latérale des Réglages, action `addAccount` du menu ; `AccountsSettingsModel.startAdding` n'ouvre aucun formulaire). Quand Pro s'arrête avec plusieurs comptes, **tous sont mis en pause sauf le premier** de la liste, sans choix (`AccountsModel.isPaused`, `activeSessions`). Un compte en pause garde sa clé, son cache et ses préférences, ne se synchronise plus et ne demande plus rien à Apple : ni rythme, ni « Actualiser », ni réveil, ni socket (`refresh` répond compte inconnu), ni « Tester la connexion ». Il reste listé, sous un cadenas, dans le sélecteur du menu, le sélecteur de la fenêtre et la barre latérale des Réglages, où son volet porte un bandeau qui l'explique ; le choisir (`AccountsModel.select`) ne l'affiche pas et appelle `onPausedSelection`, qui ouvre la feuille d'achat. Il se supprime comme un autre, et supprimer le premier rend actif le suivant. La pastille de la barre ne lit que `activeSessions` ; les notifications suivent les synchros, donc les comptes actifs. Quand Pro revient, tous repartent sans rien demander (`applyProState`, appelé à chaque changement de `ProStore` par `withObservationTracking`). **Tant que l'état de Pro n'est pas lu** (`ProStore.hasResolved`, vrai après la première lecture des transactions ou avec un état figé), les comptes après le premier attendent sans être dits en pause, et la sélection n'est pas touchée : un abonné retrouve le compte qu'il avait laissé, et personne ne synchronise sur une supposition. `BuildStore.start` relance une synchro à chaque appel : `AccountsModel` ne l'appelle qu'au passage de retenu à suivi (`heldIDs`). Côté commande, sans Pro, `cumulus status --account <compte en pause>` répond `PRO_REQUIRED` (`ProGate.pausedRefusal` : tout compte autre que le premier du registre).

**Widgets** (XCO-49, styles choisis sur maquettes le 13/10/2026) : la cible `CumulusWidgets` (extension WidgetKit, `Widgets/`, bundle ID `com.guik.xcode-cloud-companion.widgets`, embarquée dans `Contents/PlugIns`, sa propre sandbox et le même app group par `Config/CumulusWidgets.entitlements`) propose quatre widgets : « Latest Build » (petit, réglable sur une app), « Cycle » (petit, l'anneau), « Cycle and Builds » (moyen, la barre) et « Cycle Ring and Builds » (moyen, l'anneau). **L'extension ne lit qu'un fichier** : `Widgets.json` à la racine du conteneur de groupe (`WidgetSnapshot`, dans `CLI/`), que l'app écrit pour le compte affiché après chaque synchro et à chaque changement de compte (`WidgetFeed`, `WidgetFeedWriter` dans `AppDelegate` ; rien sous tests). Elle n'a ni clé, ni réseau, ni les préférences de l'app : les couleurs des apps, le pourcentage du cycle (le même arrondi que partout) et les builds y sont déjà résolus ; les widgets ne sont rechargés (`reloadAllTimelines`) que si ce contenu a changé. Pendant la mesure et sans forfait, un widget de cycle le dit au lieu d'un chiffre. **Une ligne de build** (`BuildRow`, XCO-168, vérifié hors écran le 14/10/2026 en français et en anglais) tient sur deux lignes : le point d'état et le nom de l'app sur toute la largeur (coupé par « … » seulement s'il ne tient pas), puis « workflow • âge » (l'âge est un `Text` que le système met à jour seul, `BuildAge`, et garde sa place avant le workflow). Le mot d'état n'y est plus : le point le dit par un glyphe (`BuildStateDot`, mêmes formes que `BuildStatus.systemImage` : coche, croix, point d'exclamation, tiret ; cercle creux en cours), et le libellé VoiceOver de la ligne dit l'état en toutes lettres (`WidgetSnapshot.Build.spokenLine`). Le petit widget d'anneau n'affiche que la première ligne. Un clic ouvre `cumulus://build/<id>` ou `cumulus://overview`. La cible **n'a pas** l'isolation `MainActor` par défaut (WidgetKit appelle ses fournisseurs hors du fil principal) et ne compile que trois fichiers partagés, listés à la main dans `project.pbxproj` : `CLI/WidgetSnapshot.swift`, `Menu/UsageFormat.swift`, `Sync/SharedContainer.swift`. Ses chaînes sont dans `Widgets/Localizable.xcstrings`. Le rendu se vérifie en copiant `WidgetViews.swift` dans un test jetable (les vues ne sont pas dans le module de l'app).

**App Intents** (XCO-62, 13/10/2026) : trois intents dans `Intents/` pour Siri, Spotlight et Raccourcis : « Get Latest Build » (paramètre d'app facultatif), « Get Running Builds », « Get Cycle Usage », avec leurs App Shortcuts (`CumulusShortcuts`). Aucun ne lance ni ne change un build. Ils lisent les caches par `IntentAnswers`, qui pose les mêmes questions que la commande (`CLIQueryRunner`), sans socket ni réseau ; la consommation se dit toujours comme une estimation tant qu'il reste des minutes estimées. **Isolation** : les entités (`BuildEntity`, `FollowedAppEntity`) sont `nonisolated` et n'ont pas de `@Property` (l'enveloppe est une référence non `Sendable`) ; un intent à `@Parameter` ne peut pas être `nonisolated` en entier : son `title`, sa `description` et son `init()` le sont un par un, `perform()` reste sur le `MainActor`. Un test crée et lit intents et entités depuis une tâche détachée. Les phrases des raccourcis se traduisent dans `AppShortcuts.xcstrings` (un `stringSet` par raccourci, sous la clé de sa première phrase, `${applicationName}` tel quel) ; les titres et les réponses sont dans `Localizable.xcstrings`. L'indexation Spotlight des builds n'est pas faite.

**Lancer depuis un agent** (XCO-61, décision de l'utilisateur le 11/10/2026) : `cumulus run <workflow> [--branch | --tag | --pr] [--clean] [--yes]` et l'outil MCP `start_build` passent par la méthode `launch` du socket : l'app reste la seule à écrire chez Apple, avec le `BuildLauncher` de la fenêtre (`AgentLaunchService`). La commande résout le workflow depuis le cache (`CLIReference.workflow` : nom, ou `App/Workflow` en cas d'homonymes) et, sans source, prend la branche du dernier build non-PR du workflow ; l'app résout branche, tag ou PR par `LaunchChoices`. Garde-fous : « Accès de la clé » à « Lecture + Build » (sinon `NOT_ALLOWED`, code 7 ; un 403 repasse la clé en lecture seule), au plus 3 lancements par heure et par compte, tous agents confondus (`AgentLaunchGate`, sinon `RATE_LIMITED`, code 8), les refus d'Apple en `REFUSED` (code 1) avec ses mots, jamais de second envoi. Sur un terminal, `cumulus run` demande `[y/N]` sauf `--yes` ; dans un tube ou par MCP, l'agent a décidé et l'app poste la notification « Build lancé par un agent » (réglable dans Réglages › Notifications). La règle « aucun lancement par URL ni par Raccourci » reste : seule une commande ou un outil appelé explicitement lance.

**TestFlight depuis un agent** (XCO-177, décision de l'utilisateur le 23/10/2026 : un agent peut aussi expirer un build) : `cumulus testflight <App#42 | id>` (lecture), `cumulus testflight give <build> [--group <nom>]… [--remove <nom>]… [--notes <texte> --locale <fr-FR>] [--notify | --no-notify] [--yes]` et `cumulus testflight expire <build> [--yes]`, avec les outils MCP `get_testflight`, `give_testflight_build` et `expire_testflight_build`, même architecture que `run` : la commande ne parle jamais à Apple, l'app écrit avec les services de XCO-175 et XCO-176 (`TestFlightDistributor`) par `AgentTestFlightService` (`Sync/`). **Ce que la commande lit** : `TestFlight.json` (les derniers builds de chaque app, `TestFlightStore`) et `TestFlightGroups.json` (les groupes de chaque app, `TestFlightGroupsStore`) sont déjà dans le dossier du compte du conteneur de groupe ; le build TestFlight d'un build Xcode Cloud se retrouve par `BuildDetails/<run>.json` (`betaBuilds`, les mêmes identifiants). Ce que le dossier n'a pas encore (le groupe d'une app jamais ouverte dans la fenêtre, la liste des builds TestFlight d'un build jamais ouvert), la commande le fait lire une fois à l'app par la méthode `testFlightLoad` (lecture seule, ajoutée à `testFlightGive` et `testFlightExpire` ; `--cached` ne la demande jamais, et une lecture ne démarre pas l'app, une écriture oui). **Noms de groupes** : la commande résout `--group` / `--remove` depuis le fichier, sans casse ni accents, ou par identifiant d'Apple (`CLITestFlightGroups`) : un nom inconnu répond `NOT_FOUND` avec les groupes connus en suggestions, un nom partagé par deux groupes `AMBIGUOUS` (même code de sortie 5), un groupe « reçoit tous les builds » une erreur d'usage (code 2) ; le socket reçoit des **identifiants**, pas des noms, et l'app les revérifie. **Garde-fous de l'app**, dans cet ordre : Pro (`commandLine` et `testFlightDistribution`, `IPCTestFlightReason.proRequired`), compte connu et actif (`paused` si Pro s'arrête avec plusieurs comptes), clé enregistrée, « Accès de la clé » à « Lecture + Build » (`notAllowed` ; un 403 repasse la clé en lecture seule), plafond de **10 écritures par heure et par compte, donner ou expirer confondus** (`AgentTestFlightGate`, indépendant des 3 lancements de `run` ; l'écriture est comptée avant l'envoi et rendue si Apple a refusé sans rien écrire), build connu (relu une fois chez Apple avant d'écrire, comme la carte), état qui permet d'écrire (`TestFlightDistributionCardModel.mode == .open`, sinon `buildNotReady` avec les mots de la carte), groupes connus pour l'app. Un groupe déjà tel que demandé n'est pas renvoyé (`unchanged`) ; sans rien à écrire la réponse est un succès avec `changed: false`, et un build déjà expiré aussi. Jamais de second envoi : `TestFlightDistributor` le garantit, un échec ambigu est suivi d'une lecture et rendu `uncertain` (`INTERNAL`, code 1). **À un terminal**, `give` et `expire` demandent `[y/N]` sauf `--yes` ; la question d'`expire` dit le nombre de testeurs (quand tous les groupes ont leur compte) et que ça ne se défait pas ; dans un tube ou par MCP l'agent a décidé et l'app poste « Build TestFlight donné par un agent » (ou « Groupes TestFlight modifiés par un agent » quand il n'a fait que retirer) ou « Build TestFlight expiré par un agent », réglable dans Réglages › Notifications (`BuildNotificationRules.agentTestFlight`, clé `notifications.builds.agentTestFlight`, actif par défaut), le clic ouvre `cumulus://app/<productID>`. La sortie après une écriture montre le build **relu** par l'app (fichier partagé) seulement quand cette relecture a réussi (`refreshed`), jamais l'état demandé. Notes de test : écrites seulement avec un `--group`, avec leur langue, après lecture des notes d'Apple (sinon rien n'est écrit par-dessus à l'aveugle) ; hors périmètre : « expirer le build précédent » de la feuille, jamais proposé aux agents. Le skill et `references/output-contract.md` documentent tout cela (`AgentSkillBundleTests`).

**Réglages › Agents** (XCO-64, XCO-101) : un volet des Réglages (`AgentsSettingsView`, `AgentsSettingsModel`, `AgentLinks.swift`), rangé par agent : on choisit Claude Code, Codex, Xcode ou Claude Desktop (mémorisé), et le volet liste ce qu'il lui faut avec son état (`AgentsSettingsModel.checklist(for:)`) : la commande, commune à tous, le skill pour les deux agents qui en gardent (`AgentClient.keepsSkills`), puis le serveur MCP, à copier à la main et donc jamais compté dans la progression. **Nom et icône d'une app** (XCO-73, vérifié sur le vrai compte le 10/10/2026) : l'interface affiche `CIProduct.displayName` (le nom du Store quand le produit est une app qui en a un, sinon le nom du produit). `product.name` **reste la clé** de la couleur d'une app (`AppPalette`), de ses minutes d'usage (l'export d'Apple parle en noms de produits) et des références du CLI (`App#42`, `--app`) : ne jamais les passer au nom du Store. L'icône vient de l'`iconAssetToken` d'un build : un gabarit `https://…mzstatic.com/…/{w}x{h}bb.{f}` servi sans authentification, dont le chemin finit par `.icns` pour une app Mac (dessinée telle quelle ; les autres sont des carrés pleins, arrondis dans l'app). Le menu de la barre n'affiche pas d'icône.

**Couleur d'une app** (XCO-128, vérifié sur quatre vraies icônes le 13/10/2026) : une app prend la couleur dominante de son icône (`AppSwatch.icon`), sinon une des six teintes système d'`AppPalette`, comme avant : pas d'icône, ou une icône sans teinte. `IconColorExtractor` (`Usage/IconColor.swift`, pur) range les pixels opaques de l'icône réduite à 40 × 40 par teinte Oklab, chacun pesant sa saturation ; blancs, gris et noirs ne comptent pas, et sous 3 % de pixels colorés l'icône n'a pas de couleur. `AppPalette` garde la couleur lue telle quelle, avec l'empreinte de l'icône (`IconReading`, dans la préférence de la palette du compte, donc effacée avec lui) ; `swatch(for:)` la ramène dans une plage de luminosité lisible sur fond clair comme sombre (`SwatchColor.legible`, teinte inchangée). `AccountSession.readIconColors` lit les icônes après chaque synchro réussie, hors du fil principal : une fois par icône, de nouveau quand elle change, et au plus une tentative par heure pour une image introuvable ; aucune requête à l'API, seulement l'image (cache `AppIconCache`, sinon serveurs d'images). Le menu a donc les couleurs sans la fenêtre. La fenêtre prend sa palette par `AccountSession.palette(for:summary:)`, qui la fait redessiner quand une couleur arrive. Deux apps aux icônes de même teinte ont la même couleur. Une session créée sans `iconCache` (les tests) ne lit rien. **Couleur choisie** (XCO-129, choix de l'utilisateur sur maquettes le 13/10/2026) : une couleur donnée à la main passe devant celle de l'icône (`AppPalette.Choice` : une teinte système ou une couleur libre, dans la même préférence ; `AccountSession.chooseColor`, nil pour revenir à l'icône). Un changement d'icône ne touche pas à une couleur choisie.

**Journaux d'une action** (XCO-70, vérifié sur une vraie archive le 10/10/2026) : le bouton « Journaux » (partie Actions de la fiche, et action en échec de la frise) télécharge l'artefact `LOG_BUNDLE` de l'action avec les règles d'un artefact (`LogOpener` : adresse fraîche, `ArtifactAddress`, pas de jeton), le décompresse dans `Caches/Logs/<id de l'action>/` et ouvre le dossier dans le Finder, sans panneau d'enregistrement. Une vraie archive d'Xcode Cloud est un ZIP simple (entrées stockées ou « deflate », pas de ZIP64) : `ZipExtractor` le lit à la main avec `Compression`, sans `Process` ni dépendance. Il juge tous les chemins avant d'écrire le premier octet : une entrée absolue ou avec `..` refuse l'archive entière, un lien symbolique n'est jamais créé, une taille déclarée fausse ou au-delà du plafond aussi. Le cache est plafonné à 500 Mo, les dossiers ouverts le moins récemment partent d'abord. Les journaux d'un build `COMPLETE` déjà décompressés se rouvrent sans requête. Le bouton s'affiche pour toute action terminée tant qu'on ne sait pas qu'elle n'a pas d'archive : la liste des artefacts n'est pas demandée d'avance.

**En bref et groupes suggérés** (XCO-157, Pro) : sur la fiche d'un build `FAILED` ou `ERRORED` terminé, la carte « En bref » (`FailureInsightCard`, juste avant « Pour une IA », `.detailPlacement(.side)`, identité stable) dit la **catégorie** dans une capsule et, quand le modèle a donné quelque chose, une phrase écrite **sur ce Mac** par Apple Intelligence (`FoundationModels`, aucun envoi), avec en pied, en toutes lettres, « Généré sur ce Mac par Apple Intelligence · peut contenir des erreurs ». La catégorie n'est jamais celle du modèle : `FailureCategory.decide` la tire des données du build (signature d'abord, puis erreur dans un fichier ou étape du compilateur = compilation, erreurs d'une étape de distribution seule = `distribution`, autres erreurs = configuration, tests en échec tous `MIXED` = instable, sinon tests ; `infrastructure` pour un build `ERRORED` sans rien d'autre) et elle est donnée au modèle comme un fait. Le modèle écrit un titre (90 caractères, une phrase) et, à partir de 6 tests en échec, des groupes de tests par leurs index ; `FailureInsightValidator` refuse un titre trop long, à plusieurs phrases, ou qui cite un nom de fichier ou un nombre absents des données (une relance plus ferme, puis rien), et nettoie les groupes (index hors liste ou déjà pris, titre vide ou long ; moins de deux groupes = aucun). **Quand ça charge** : `FailureInsightStore.load`, appelé par la `.task(id: run.id)` de la carte, lit le disque, sinon charge problèmes et tests comme `BuildFailureCopier` (disque d'abord, jamais sous `SyncSchedule.criticalRemaining`), calcule la catégorie (sans données lues : pas de carte, rien de gardé) puis demande au service, hors du `MainActor`, un seul à la fois. Pendant tout ce temps, dès la première image, la carte est son propre squelette (voir « Squelettes de chargement »), puis elle disparaît si rien n'est venu. C'est le seul endroit où ouvrir la fiche d'un build en échec charge ses problèmes et ses tests. **Cache** : `Accounts/<id>/FailureInsights/<build>-<fr|en>.json` (`FailureInsightRecord`, supprimé avec le compte par `AccountPaths.deleteAll`, et à la réinitialisation de la clé), jamais régénéré une fois écrit ; un modèle qui ne donne rien (erreur, refus du validateur) est gardé aussi, avec la seule catégorie ; les groupes sont gardés par identité de test (action + classe + nom), les index étant résolus juste après la génération. La langue est le français quand l'app tourne en français **et** que le modèle l'écrit, l'anglais sinon. **Trois conditions** (`FailureInsightFeature.mode`, la seule réponse) : Apple Intelligence disponible, réglage Général › « Résumer les builds en échec avec Apple Intelligence » actif (clé globale `failureInsight.enabled`, vrai par défaut ; grisé avec sa raison si le modèle manque), et Cumulus Pro (`ProFeature.failureInsight`). Sans modèle ou réglage coupé : rien nulle part, Pro ou non. Avec les deux mais sans Pro : `ProLockedCard` à la place de la carte, rien ne se lit ni ne se génère. `AccountSession` pose `FailureInsightStore.isOpen` ; sous tests le service refuse toute demande (`UnavailableInsightGenerator`). **Onglet Tests** : avec des groupes et au moins 6 tests en échec, un sélecteur « Groupes suggérés | Par classe » (ouvert sur les groupes) ; `SuggestedTestSections` (pur) range chaque test une fois, dans son groupe ou dans « Autres », 3 lignes puis « Afficher n de plus » ; « Par classe » est la liste d'avant. Libellés « suggérés » et non « trouvés » : **mesuré** sur 24 vrais builds (13/10/2026), la catégorie est juste sur 22 ; les groupes n'ont été jugés que sur des jeux écrits à la main, où une cause entière a manqué chaque fois.

**Notifications** (XCO-47) : locales, sans serveur ni entitlement. `AccountsModel.onSync` donne, pour chaque compte, l'instantané d'avant et d'après chaque synchro réussie ; un build « vient de finir » quand il était en cours avant et `COMPLETE` après (ou créé puis terminé entre deux synchros), depuis moins d'une heure. La première synchro d'un compte dans une session ne notifie rien. Tous les comptes notifient, quel que soit celui affiché ; avec plusieurs comptes, la bannière porte le nom du sien en sous-titre. L'autorisation n'est demandée qu'au moment d'envoyer la première bannière, ou par le bouton de l'onglet Notifications des Réglages : jamais au lancement. Un build bloqué (action `RUNNING` au-delà de N fois la médiane de la même action réussie du workflow, trois échantillons au moins) est signalé une fois, y compris après un redémarrage. Le clic ouvre l'adresse `cumulus://` portée par la bannière. **Bannière d'un build en échec** (XCO-157) : quand la fonction « En bref » est ouverte pour le compte (`FailureInsightSource.isOpen`, donc `FailureInsightFeature.mode == .open`), la bannière de fin d'un build `FAILED` ou `ERRORED` attend `FailureInsightStore.load` au plus 5 s (`FailureBannerFormat.waitLimit`, `BannerWait`), puis part **une seule fois**, depuis sa propre tâche (`NotificationCoordinator.postFailure`) : les autres bannières de la synchro (réussite, annulation, build bloqué, lancement par un agent, forfait) partent aussitôt, et la synchro ne l'attend pas. Elle passe après tous les filtres existants (app muette, réglages, moins d'une heure, première synchro d'un compte dans la session), donc rien n'est demandé pour un build qui ne notifie pas ; `load` étant idempotent, les problèmes et tests d'un build ne sont lus qu'une fois, et une fiche déjà ouverte qui charge le même build est attendue (`StoreFailureInsightSource`). `FailureBannerFormat.notification` (pur) compose la bannière. **Un seul compte** : titre inchangé, sous-titre « catégorie · workflow », corps = la phrase, ou le corps d'avant sans phrase. **Plusieurs comptes** : le sous-titre reste le nom du compte, le corps devient « catégorie · phrase » (ou « catégorie · corps d'avant »). Pas prête en 5 s, ou sans fiche : la bannière d'avant, telle quelle, postée à la 5e seconde, sans seconde bannière ni mise à jour ; le chargement continue et la fiche du build le trouve en cache. Fonction fermée (pas d'Apple Intelligence, réglage coupé, pas de Pro) : la bannière d'avant, sans attente ni requête. Même identifiant de bannière, même adresse `cumulus://build/<id>`. Sous tests, la source est une doublure (`FailureInsightSource`) et `settleFailureBanners()` attend les bannières en cours. `NotificationResponder` est `nonisolated` : le centre de notifications l'appelle hors du fil principal. Le délégué n'est posé que hors tests, et les tests passent par un `NotificationPosting` simulé. En Debug, `XCC_NOTIFY=1` poste une bannière d'essai après la première synchro.

**Volet Notifications** (XCO-100) : l'autorisation est un bandeau en tête (vert quand macOS laisse passer les bannières, sinon le bouton qui y mène) ; les états de fin de build portent leur glyphe (`StatusBadge`), le seuil de blocage est un sélecteur segmenté sur `BuildNotificationRules.stuckFactors`, et chaque app a son icône ou son initiale. Aucune préférence n'a changé de clé.

**Alertes vers un webhook** (XCO-147, Pro, 14/10/2026) : Réglages › Notifications, groupe « Envoyer aussi ailleurs », propre à chaque compte (un seul compte : le groupe porte directement les champs ; plusieurs : un groupe par compte, titré de son nom ; un compte en pause est grisé avec la raison, comme tout le groupe sans Pro, adresse et choix conservés). L'**adresse est un secret** : un élément du trousseau par compte (`KeychainWebhookAddressStore`, service à part, `kSecAttrAccount` = identifiant du compte, doublure `InMemoryWebhookAddressStore`), jamais dans les préférences, le cache, le journal système ni `Accounts.json` ; seul son hôte se lit (`WebhookSettingsModel.host`, affiché `hooks.slack.com/••••••••`), « Remplacer… » rouvre un champ masqué vide, « Retirer » efface après confirmation ; `WebhookSettingsModel.commit` d'un champ vide efface aussi, mais le bouton « Enregistrer » est grisé à vide et Entrée n'y fait rien, pour qu'un geste de trop n'efface pas l'adresse. Seul `https://` avec un hôte est accepté (`WebhookAddress`), le refus se lit sous le champ ; aucune description de l'adresse n'en montre autre chose que l'hôte. `AccountSession.erase` retire l'adresse **avant** la clé (si le trousseau refuse, le compte reste entier) ; `AccountDefaults.names` porte `webhook.events` (`WebhookChoices` : forfait, bloqué, échec cochés, réussi non) et `webhook.usageAlertState`. **Le message est la bannière déjà composée** (`WebhookMessage(banner:)` : titre, sous-titre, corps, adresse `cumulus://`), en texte simple sur des lignes (`text`) ; le corps suit l'hôte : `hooks.slack.com` reçoit `{"text"}`, `discord.com/api/webhooks` `{"content"}` (2 000 caractères au plus), toute autre adresse `event` (`usage_alert`, `build_stuck`, `build_failed`, `build_succeeded`, `test`), `title`, `body`, `url`, `isEstimate`, `text`, et `app`, `workflow`, `build` quand l'alerte en a ; `account` n'est ajouté qu'avec plusieurs comptes (écart au ticket, qui ne le listait pas), jamais l'Issuer ID, le Key ID ni une adresse de téléchargement. **Quatre événements seulement** : alerte de forfait (75 %, 90 %, rythme), build bloqué, build en échec (`FAILED`, `ERRORED`), build réussi ; ralentissement, incident Apple, lancement par un agent et annulation ne partent pas. **Indépendant des bannières** : `NotificationCoordinator.buildsDidSync` demande au service ce que le compte envoie (`WebhookService.choices`, nil sans Pro, sans adresse ou pour un compte en pause), calcule les fins de build et les builds bloqués avec les règles des bannières **unies** à celles du webhook, puis chaque élément va à la bannière et/ou au webhook selon son propre choix ; les garde-fous sont ceux des bannières (app muette, moins d'une heure, première synchro d'un compte, build bloqué une fois par la mémoire commune). L'alerte de forfait du webhook a **son propre état** (`webhook.usageAlertState`) : une alerte par seuil et par cycle, quels que soient les seuils cochés pour les bannières. Un build en échec part du même `postFailure` que sa bannière, une fois « En bref » connu ou l'attente de 5 s écoulée (catégorie et phrase comprises). `WebhookService.send` ne bloque ni la synchro ni les bannières (une tâche par envoi) ; il revérifie événement, Pro, compte actif et adresse, envoie en `POST` `application/json` par une session éphémère (`URLSessionWebhookSender`, délai de 10 s, aucune redirection suivie : rien ne part vers une autre adresse que celle saisie), et **un seul nouvel essai 30 s plus tard** pour une erreur réseau ou un 5xx, aucun après un 4xx (le contrôle est refait avant le nouvel essai : Pro perdu, compte retiré, adresse changée). « Dernier envoi » (heure et résultat : envoyé, refusé avec le code, injoignable) est gardé en mémoire pour la session, jamais l'adresse. « Envoyer un essai » (une tentative, message « Test from Cumulus ») ne dépend pas des événements choisis. Sous tests `AppDelegate` donne `UnreachableWebhookSender` : rien ne part, aucun test n'appelle le réseau. L'app a déjà l'accès réseau sortant (`ENABLE_OUTGOING_NETWORK_CONNECTIONS`). Le critère de texte pour la politique de confidentialité reste à l'utilisateur. Hors périmètre : envoi quand le Mac est éteint, OAuth Slack, messages riches, plusieurs adresses par compte.

**Alerte de forfait** (XCO-65) : `UsageAlertPlanner` lit le même `UsageSummary` que le menu, après chaque synchro : 75 % puis 90 % du forfait, et le rythme (`exhaustionDate`). Une alerte par seuil, par cycle et par compte, mémorisée dans les préférences (`UsageAlertState`) et remise à zéro quand le cycle change ; rien pendant la mesure du premier chargement ni sans forfait. Chaque message dit que le chiffre est une estimation tant qu'il reste des minutes estimées ou que l'export a plus de trois jours. Le clic ouvre `cumulus://overview?account=<id>`, la Vue d'ensemble du compte concerné.

**Incident Apple sur Xcode Cloud** (XCO-162, gratuit, 14/10/2026) : un build qui s'arrête sans erreur de code est souvent l'affaire d'Apple ; la fiche d'un build `ERRORED` le dit quand la page d'état des services d'Apple (`https://www.apple.com/support/systemstatus/data/developer/system_status_en_US.js`, sans authentification) liste un événement qui couvre son arrêt. **Vérifié le 13/10/2026** : le corps est `jsonCallback({"drMessage":null,"services":[{"serviceName":…,"redirectUrl":…,"events":[…]}],"drpost":false});` ; un événement réel (4 octobre, sur « Apple Music for Artists », pas sur Xcode Cloud) porte `messageId`, `statusType`, `message`, `datePosted`, `startDate`, `endDate`, `epochStartDate`, `epochEndDate` (millisecondes), `usersAffected`, `affectedServices`, `eventStatus` (« resolved »). **Aucun événement en cours n'a été vu** : sa forme est une hypothèse (le même événement, `eventStatus` à `ongoing`, sans `epochEndDate`). `AppleStatusDecoder` (pur) est donc tolérant : un événement est en cours s'il n'a pas de fin, une fin nulle ou à zéro, quel que soit le texte de `eventStatus` ; le service se cherche par son nom sans les blancs perdus (Apple en laisse), et tout ce qui diffère (enveloppe, service absent, `events` qui n'est pas une liste, début absent ou non numérique, fin d'un autre type) donne `AppleStatusReading.unknown`, jamais une erreur et jamais « tout va bien ». Les fixtures de test sont la vraie page réduite (`appleSystemStatus-resolved-elsewhere.json` : Xcode Cloud sans événement, et le service qui porte le vrai événement) et sa variante supposée (`appleSystemStatus-assumed-ongoing.json`, dont le test dit « assumed »). Un événement **couvre un arrêt** quand [début du build, fin du build] recoupe [début de l'événement, sa fin ou maintenant] (`AppleStatusEvent.covers`, `AppleStatusKnowledge.event(covering:now:)`, le plus ancien s'il y en a plusieurs). **Cadence** (`AppleStatusSchedule`, pur) : aucune lecture de fond ; une lecture, au plus une par 10 min (les tentatives comptent, réussies ou non), déclenchée soit par un build d'un compte actif qui finit `ERRORED` vu à la synchro (`AppleStatusStore.buildsDidSync`, branché sur `AccountsModel.onSync` ; la première synchro d'un compte dans la session est exclue ; indépendant des réglages de notification et des apps muettes), soit par l'ouverture de la fiche d'un build `ERRORED` fini depuis moins de 24 h (`sheetDidOpen`, `.task(id: run.id)`). La requête est un `GET` sans paramètre ni en-tête ajouté, en session éphémère sans cookie, cache ni identifiants (`URLSessionAppleStatusFetcher`) : ni jeton de l'API, ni identifiant, ni donnée de l'utilisateur ; l'entitlement réseau sortant existait déjà. **Ce que l'app sait expire** : un événement en cours n'est connu que 30 min après la dernière lecture réussie (`AppleStatusKnowledge.ongoingLifetime`) ; un événement clos reste connu ; rien n'est écrit sur disque. **Où ça se dit** : le bandeau `AppleStatusBanner`, premier groupe de la fiche (`.detailPlacement(.full)`, seulement pour un build `ERRORED` dont l'arrêt est couvert) : « Apple signale un incident sur Xcode Cloud depuis 14 h 10 » (« Apple a signalé un incident … de x à y » une fois clos), « Ce build s'est arrêté à … », « D'après la page d'état des services d'Apple », « Voir la page d'état » (`https://developer.apple.com/system-status/`) et, tant que l'incident dure, « Prévenir quand c'est rétabli ». **Le texte d'Apple (en anglais) n'est jamais affiché** : seulement les mots de l'app et les heures, dans le fuseau du Mac (l'heure seule le jour même, avec le jour sinon). Sans événement qui couvre l'arrêt : rien, l'app n'affirme jamais que tout va bien. Le menu de la barre porte, en tête, « Xcode Cloud : incident en cours chez Apple » (un triangle teinté puis les mots, ligne qui ouvre la page d'état) tant qu'un incident en cours est connu (`StatusMenuState.hasAppleIncident`). **Veille** (`AppleStatusStore.startWatching`) : « Prévenir quand c'est rétabli » relit la page toutes les 5 min, 12 h au plus (`AppleStatusSchedule.watchOutcome`, pur) ; seule une page lisible qui ne liste plus d'événement en cours la termine (une lecture qui échoue ou une page `unknown` ne conclut rien) ; la bannière « Xcode Cloud est rétabli » dit alors combien de builds `ERRORED` des comptes actifs ont fini pendant l'incident et ouvre `cumulus://builds`. Elle passe par `NotificationCoordinator.deliver` ; l'autorisation est demandée au clic sur le bouton (là où l'utilisateur regarde), pas à la bannière. **La veille vit en mémoire** : si l'app quitte, elle est perdue et le bouton redevient « Prévenir quand c'est rétabli ». Une fois demandé, il devient « Cumulus préviendra quand c'est rétabli ». **Aucune relance de build, nulle part** : ni bouton ni action qui lance quoi que ce soit. Sous tests, `AppDelegate` crée le store sans lecteur : rien ne part. En Debug, `XCC_APPLE_STATUS=incident|resolved` fige l'état (un incident commencé la veille, en cours ou clos depuis une heure), sans rien lire ni expirer. Le rendu hors écran de la fiche (un build `ERRORED` avec le bandeau, avant et après « Prévenir », en clair et en sombre, sur une et deux colonnes) a été regardé le 14/10/2026 ; la vraie page n'a été lue que par le relevé du 13/10/2026, jamais sous un incident en cours.

**Piège d'isolation** (vérifié le 10/10/2026) : dans ce module à isolation `MainActor` par défaut, une fermeture écrite dans une fonction `nonisolated` d'un type `MainActor` (une vue, par exemple) reste isolée au `MainActor` et **plante à l'exécution** hors du fil principal (`dispatch_assert_queue`). Mettre ce code dans un type `nonisolated`. Le lanceur de tests relance l'hôte et affiche quand même « passed » : après un doute, compter les rapports `Cumulus-*.ips` dans `~/Library/Logs/DiagnosticReports`.

**Dossier surveillé** (XCO-171, refus de la revue du 21/10/2026, guideline 2.4.5(i)) : Apple a refusé la 1.0 (build 9) parce que l'entitlement `com.apple.security.files.downloads.read-only` n'avait pas de fonction visible (et que sa phrase d'usage était floue, guideline 5.1.1(ii)). **Cet entitlement ne revient jamais** (`ENABLE_FILE_ACCESS_DOWNLOADS_FOLDER` n'est plus dans le projet) ; l'app n'a que `user-selected.read-write`. **Aucun dossier n'est surveillé tant que l'utilisateur n'en a pas choisi un** : Réglages › compte › Minutes facturées › « Choisir un dossier… » ouvre le panneau standard (dossiers seulement, ouvert sur le vrai Téléchargements, construit depuis `getpwuid` car `URL.downloadsDirectory` pointe dans le conteneur sous sandbox), « Modifier… » et « Arrêter la surveillance » suivent. `WatchedFolder` (`Usage/`) garde le choix en signet à portée de sécurité dans les préférences (clé `usage.watchedFolder`) : **global à tous les comptes**, l'import étant déjà commun, donc hors de `AccountDefaults.names`. Un signet périmé est renouvelé tant que le dossier est lisible, sinon oublié ; un dossier disparu vaut « aucun dossier », jamais une erreur. `AccountsModel.watchedFolder` l'expose aux Réglages ; `UsageImporter` tient `startAccessingSecurityScopedResource()` tant qu'il surveille, le relâche à l'arrêt (veille comprise), au changement ou à l'oubli, et un nouveau choix relance la surveillance et lit le dossier aussitôt, avec les mêmes règles (routage par apps, chaque fichier lu une fois). L'import manuel (« Importer un export… ») ne dépend pas du dossier. `UsageStore` ne surveille plus rien par défaut.

**Source des minutes** (XCO-6, mesuré sur 55 builds réels le 09/10/2026) : Apple facture **par machine**. Chaque destination de test paie son temps d'exécution (`destinationTestResults[].duration`, sommé par appareil) plus ~4,5 min de préparation, et deux fois ses tests quand l'un d'eux échoue (rejoué) ; une archive réussie paie son calcul seul, pas l'envoi à TestFlight : on prend son passage réussi le plus court. Le tout dans `MachineModel`. Résultat : +2 % sur 30 jours, 4 min d'écart moyen par build, sauf certains échecs rejoués (jusqu'à −40 min). La durée murale d'un test ne dit **ni** le nombre de simulateurs **ni** leur attente : ne jamais l'additionner. L'export CSV d'Apple (XCO-14) reste la source exacte quand il est importé.

**Pièges de la barre des menus** (vérifiés sur le vrai bouton le 09/10/2026) :
- L'image du bouton vient des symboles du catalogue (`MenuBarIcon`), ou de l'anneau du build en cours (voir « Temps restant d'un build ») : `logo` seul en template, ou `logo.badge` en palette (pastille = niveau primaire, à la couleur de l'état ; nuage = niveau secondaire, à la couleur du texte résolue **au dessin**, sinon il prend l'apparence de l'app et non celle de la barre). Les deux se chargent par `NSImage(symbolName:bundle:)`. Aucune vue n'est posée sur le bouton. **L'icône de l'app s'appelle `AppIcon`** (`AppIcon.icon`, Icon Composer ; `ASSETCATALOG_COMPILER_APPICON_NAME`) : jusqu'au build 8 elle s'appelait `logo`, comme le symbole, et App Store Connect a refusé la soumission faute d'« icône de 1024 × 1024 » alors que le catalogue en contenait une (XCO-170, 14/10/2026). Ne jamais redonner à un symbole ou une image le nom de l'icône.
- Une icône ajoutée alors que la barre est pleine est **masquée** (icône « « » de débordement) : pour voir sa propre instance, libérer de la place ou quitter une autre instance de l'app.
- En Debug, `XCC_BADGE=running|failed|succeeded|stopped|none` force la pastille de la barre ; `running` fait aussi dessiner l'anneau d'un build fictif de deux actions, la seconde en cours (`MenuBarRing.sample`), qui finit dans `XCC_ETA` minutes (4 par défaut).
- En Debug, `XCC_ETA=<minutes>` force le texte du temps restant de la barre (un build, autant de minutes ; avec `XCC_BADGE=running` pour la pastille et l'anneau). Le réglage « Afficher le temps restant dans la barre des menus » reste obéi.
- En Debug, `XCC_APPLE_STATUS=incident|resolved` force l'état des incidents Apple sur Xcode Cloud (bandeau de la fiche d'un build `ERRORED`, ligne du menu), sans lecture.
- `NSMenuItem.badge` n'accepte ni couleur ni style : l'âge des builds et les minutes des apps y sont des textes courts ; les points d'état et le carré de couleur d'une app sont des caractères teintés (« • », « ◉ », « ■ ») en tête du titre attribué : le menu n'affiche **aucune** `NSMenuItem.image` (ni dessinée, ni symbole SF), vérifié le 09/10/2026.

**Écriture : lancer ou relancer un build** (XCO-43, la première des requêtes qui modifient quelque chose chez Apple) : `POST /v1/ciBuildRuns`, **jamais rejouée par l'app**, même après un timeout ou un 5xx. Un échec ambigu relit d'abord `GET /v1/ciWorkflows/{id}/buildRuns?limit=1&sort=-number` (`BuildLauncher`), l'interface ne propose un nouvel essai qu'après. **Une réponse 2xx vaut lancement, quoi qu'on sache lire de son corps** (XCO-127 ; vu le 12/10/2026 dans le journal système : Apple a répondu 201, le corps n'a pas décodé, et la liste relue une demi-seconde plus tard ne montrait pas encore le build) : `startBuildRun` rend le build dès que son identifiant se lit, et la liste est relue jusqu'à quatre fois (`BuildLauncher.lookDelays` : tout de suite, puis 2, 4 et 8 s ; arrêt sur un 429). Trois issues se distinguent : `.accepted` (2xx, pas encore listé : ne pas relancer), `.uncertain(found: nil)` (liste lue, aucun nouveau build), `.unknown` (liste illisible : on ne sait pas). Ce qui n'a pas pu être lu part au journal système (`LaunchLog`, sous-système `com.guik.xcode-cloud-companion`, catégorie `launch`) : `/usr/bin/log show --predicate 'subsystem == "com.guik.xcode-cloud-companion"'` (dans zsh, `log` seul est une commande interne). Le corps n'envoie `clean` que s'il vaut `true`, un lancement a une seule source (branche/tag ou PR), une relance aucune. La feuille de lancement (XCO-48) propose les branches, les tags et les pull requests ouvertes du dépôt du workflow (`LaunchChoices` : `gitReferences` puis `GET /v1/scmRepositories/{id}/pullRequests`, filtré sur `isClosed`), lus une fois par session par `BuildLauncher.choices` ; si la liste des PR échoue, branches et tags restent proposés. Sous le menu, `LaunchSourceHistory` dit le dernier build du cache sur cette source ; au-delà de 12 noms un champ filtre la liste, qui n'en affiche jamais plus de 60. Le réglage « Accès de la clé » (Réglages › Comptes, `KeyAccess`, XCO-74, propre à chaque compte : `SettingsModel.keyAccess`) vaut « Lecture + Build » par défaut : chaque écriture passe déjà par une confirmation, et masquer les boutons les rendait introuvables. **Ouvrir un fichier dans Xcode** (XCO-91, vérifié le 11/10/2026) : Apple nomme les fichiers d'un problème ou d'un test comme la machine de build les voit (`/Volumes/workspace/repository/…`). `RepositoryFileLocator` en tire le chemin dans le dépôt (ce qui suit `repository/`, jamais de `..`) et le pose dans le clone local ; `LocalRepositories` (une par compte, `AccountDefaults.localRepositories`) garde le dossier choisi dans un panneau pour chaque app (clé : nom du produit), en signet à portée de sécurité, et le lève à chaque ouverture. `SourceOpener` ouvre le fichier à la ligne avec le `xed` **d'Xcode** (`Xcode.app/Contents/Developer/usr/bin/xed`, par `Process`) : `/usr/bin/xed` est un shim `xcrun` qui refuse de tourner dans la sandbox. **Écriture : retoucher un workflow** (XCO-90, la troisième écriture) : `PATCH /v1/ciWorkflows/{id}` dont le corps ne porte **que ce qui a changé** (`WorkflowUpdateRequest.changes` : nom, description, `clean`, relations `xcodeVersion` et `macOsVersion`), **jamais rejouée**. `WorkflowEditor` suit les règles du lancement et de la pause : « Modifier… » visible seulement si « Accès de la clé » vaut « Lecture + Build » et si le workflow n'est pas `isLockedForEditing`, 403 → lecture seule, 409 et 422 montrent les mots d'Apple ; un échec ambigu est suivi d'une **lecture** (`GET` du workflow avec ses versions), pas d'un second essai. **Écriture : distribuer un build TestFlight** (XCO-175, Pro, `ProFeature.testFlightDistribution`, option A « groupes cochés dans la carte » retenue le 23/10/2026) : la quatrième écriture. Garde-fous du lancement : carte visible seulement si « Accès de la clé » vaut « Lecture + Build » (sinon l'état « La clé de ce compte est en lecture seule » et « Ouvrir les Réglages… »), `isKeyWritable` et `allowed` (Pro) revérifiés par le service, qui n'envoie ni ne lit rien sans eux. **États** (`TestFlightDistributionCardModel.Mode`) : en traitement et expiré (groupes grisés, une phrase), traitement échoué, conformité à l'exportation manquante (`TestFlightBetaState.missingCompliance`, pas de groupes, « Ouvrir dans App Store Connect »), clé en lecture seule, refus 403, envoi en cours (roue sur les lignes concernées, bouton « Envoi… »), refus d'Apple (ses mots, « Rien n'a été changé. », bouton vers App Store Connect). **Deux comportements d'Apple non constatés sur le vrai compte, isolés chacun dans une seule fonction** (à constater avec la clé de Cumulus, puis ajuster) : (#8) l'ajout à un groupe externe crée-t-il seul la soumission en revue bêta ? `TestFlightDistributor.needsBetaReview(_:)` suppose que non : après l'ajout, le build est relu, et `POST /v1/betaAppReviewSubmissions` n'est envoyé que s'il n'a pas de soumission (`review == nil`) et que son état externe est « prêt à soumettre » ; un build illisible n'est jamais soumis à l'aveugle ; (#9) « Prévenir les testeurs » est le réglage `autoNotifyEnabled` du `buildBetaDetails` du build (`BuildAutoNotifyRequest`, `PATCH /v1/buildBetaDetails/{id}`, seulement s'il diffère de ce qu'Apple dit déjà, `DistributionRequest.writes`) ; `POST /v1/buildBetaNotifications` n'est pas utilisé. Les identifiants de groupe, de build et de langue vont dans des corps JSON et des chemins : lettres, chiffres et tirets seuls (`isWellFormed`), sinon rien ne part.

**Écriture : expirer un build TestFlight** (XCO-176, Pro, même verrou `ProFeature.testFlightDistribution`, planche `Expire.dc.html` du 23/10/2026) : la cinquième écriture. `PATCH /v1/builds/{id}` dont le corps ne porte **que** `expired: true` (`BuildExpirationRequest` ; jamais `expired: false`, Apple n'a pas de retour), **jamais rejouée**. `TestFlightDistributor.expire(buildID:)` (la fonction que le socket de XCO-177 appellera, sans la vue) rend une `ExpirationOutcome` : `expired` (avec le build relu par `TestFlightStore.reread`, qui est la lecture de XCO-175 : elle demande `expired` parmi les champs du build), `notAllowed` (403, clé en lecture seule), `refused` (409 et 422 : les mots d'Apple), `rateLimited`, `failed` (rien n'est parti), `uncertain` (délai, 5xx : le build est **relu**, jamais un second `PATCH` ; un build relu comme expiré vaut `expired`). **Où** : sur la carte TestFlight d'un build, un bouton « … » (« Plus d'actions ») ouvre un menu : « Copier le numéro de build », « Ouvrir dans App Store Connect », puis « Expirer ce build… » en rouge, proposé seulement pour un build traité, non expiré, clé à « Lecture + Build » (`TestFlightExpiration.isOffered`, `TestFlightDistributionCardModel.canExpire`). La confirmation est une `NSAlert` (`ExpirationAlert`) dont **« Annuler » est le bouton par défaut** et « Expirer » le destructif ; elle nomme l'app et le build, dit combien de testeurs (somme des groupes quand tous les comptes sont connus, donc un testeur dans deux groupes compte deux fois) et quels groupes le perdent, que la revue bêta en cours s'arrête s'il y en a une, et qu'une expiration ne se défait pas. Après la réponse, la carte montre celle d'Apple : groupes grisés, « Expiré le 23 oct. », plus aucune action de distribution. **Piège de la date** : Apple ne dit pas si `expirationDate` bouge quand un build est expiré à la main (non constaté sur le vrai compte) ; `TestFlightText.statusLine` n'écrit donc jamais une date à venir : il prend `expirationDate` si elle est passée, sinon `TestFlightObservation.expiredSeenAt` (l'heure de la lecture qui a vu le build passer à expiré, comme les autres observations), sinon le seul mot « Expiré ». **Case de la feuille** : « Expirer <build précédent> » (décochée, seulement quand la feuille ajoute des groupes) est proposée quand `PreviousBuild.find` trouve, parmi les builds plus anciens de la même app lus par `TestFlightStore.builds(forAppID:)`, le plus récent encore en test (état « en test » pour au moins un de ses groupes) et non expiré ; sous-texte « Encore en test pour n groupes. Ne se défait pas. ». `TestFlightDistributor.distribute(_:thenExpiring:)` n'envoie l'expiration **qu'après des groupes acceptés** (`DistributionResult`), jamais pour un envoi refusé ou incertain, jamais sur le nouveau build ; son échec est dit à part sur la carte (« 1.4 (411) n'a pas été expiré. … Les groupes du nouveau build ont été mis à jour. ») sans toucher au nouveau build. Un 403 repasse la clé en lecture seule dans les deux cas. Rendu hors écran vérifié le 23/10/2026 en clair et en sombre (carte, après, en cours, deux échecs, feuille) ; l'alerte système ne se dessine pas hors écran, son contraste en sombre est celui du système. **Non constaté sur le vrai compte** : le rôle de clé requis (Admin ou App Manager supposé), et ce que devient `expirationDate`.

**Version d'Xcode dépassée** (XCO-89) : la synchro inclut `xcodeVersion` avec les workflows (`CIWorkflow.xcodeVersion`, le numéro nu) et lit `GET /v1/ciXcodeVersions` une fois par jour (`BuildSnapshot.xcodeVersions`, même rythme que les icônes, nouvel essai dans l'heure après un échec). Apple ne marque ni la dernière ni les bêtas : `XcodeVersionCheck` (`CLI/`, pur) prend la plus haute `version` dont le `name` ne dit pas « beta », « Release Candidate » ou « RC », compare par composants, et ne signale qu'une version strictement inférieure (un workflow réglé sur « dernière version » ne se distingue pas de l'un figé sur la version du moment). Bandeau en tête de la fiche du workflow (« Modifier… » quand la retouche existe, sinon « Ouvrir dans App Store Connect »), point `arrow.up.circle` dans la barre latérale, `latestXcodeVersion` dans `cumulus workflows`.

**Builds planifiés** (XCO-88) : la synchro demande `scheduledStartCondition` avec les workflows (aucune requête de plus) ; `CIStartConditions.schedule` (`CISchedule` : fréquence, jours au sens de `Calendar`, heure, minute, fuseau, branches) vit dans l'instantané. `ScheduleForecast` (`CLI/`, pur) calcule le prochain passage dans le fuseau du déclencheur (`Calendar.nextDate`), le nombre de passages d'ici la fin du cycle et leur coût d'après `WorkflowUsage.averageMinutes` ; la section « À venir » de la Vue d'ensemble les liste (workflows actifs seulement) et dit le total comme une estimation ; rien sans forfait. `cumulus workflows` expose `nextScheduledRun`.

**Tendances d'un workflow** (XCO-87) : sous les tests de la fiche d'un workflow, `WorkflowTrendsSection` montre la durée médiane, l'attente médiane en file (`startedDate − createdDate`) et le taux de réussite des 30 derniers builds terminés (annulés et ignorés exclus), avec la dérive des 10 plus récents par rapport aux précédents (rien sous 6 builds, « stable » sous ±15 %), et un histogramme des durées, échecs en rouge, dont chaque barre ouvre le build. Tout est calculé par `WorkflowTrends` (`CLI/`, pur, partagé avec `cumulus workflows` qui l'expose en `trends`) depuis l'instantané : aucune requête, redessiné à la synchro seulement.

**TestFlight** (XCO-164, Pro, étude sur le vrai compte le 13/10/2026) : la vue d'ensemble d'une app a une carte « TestFlight » (trois builds au plus : version « 1.4 (412) », testeurs, état en un mot dans une capsule avec son symbole, « Expire dans n jours » sous 14 jours, un build expiré en grisé « Expiré le 2 oct. »), la fiche d'un build réussi qui a livré a « Du commit aux testeurs » (`TestFlightTimelineCard`, côté droit, sous la carte TestFlight gratuite qui ne change pas), et deux bannières partent fenêtre fermée. **Une seule requête par app** (`AppStoreConnectEndpoint.testFlightBuilds`) : `GET /v1/builds?filter[app]=<appID>&sort=-uploadedDate&limit=5` avec `include=buildBetaDetail,preReleaseVersion,betaAppReviewSubmission,betaGroups`, ces quatre relations **nommées aussi dans `fields[builds]`** (sinon Apple ne rend que des liens). 5 builds : environ 15 Ko et une seconde ; 200 builds dépassent le délai de 30 s. `/v1/builds/{id}/betaGroups` répond 403 pour toute clé (« GET_RELATED » non offert) : les groupes viennent de `include`. Apple ne date que l'envoi (`uploadedDate`), l'expiration (`expirationDate`) et l'envoi en revue (`submittedDate`, seulement avec une soumission) ; **la fin du traitement, l'approbation et la mise à disposition sont des états sans date**. Les valeurs vues sont `VALID`, `IN_BETA_TESTING`, `READY_FOR_BETA_TESTING`, `READY_FOR_BETA_SUBMISSION`, `EXPIRED`, `APPROVED` ; « en traitement », « en revue » et « refusé » ne l'ont **pas** été (décodés d'après les noms documentés par Apple), et toute autre valeur se lit « inconnue » sans erreur (chaque énumération a son `init(from:)` de repli). `TestFlightBuild.status(at:)` (pur) donne l'état : expiré, en traitement, traitement échoué, refusé, en revue, en attente de revue, disponible (en test avec un groupe, interne ou externe), prêt (traité, dans aucun groupe), sinon inconnu ; la revue passe avant « disponible » (un build qui teste en interne en attendant sa revue reste « en attente »). Les testeurs se lisent dans les groupes et dans les états (Apple ne liste pas toujours le groupe interne qui reçoit tous les builds). **Le store** (`TestFlightStore`, `AccountSession.testFlight`, `TestFlight.json` dans le dossier du compte, effacé avec lui et à la réinitialisation de la clé) lit **après chaque synchro réussie** (`AccountsModel.follow`) les apps dont un workflow livre à TestFlight (`CIWorkflow.shipsToTestFlight`, la règle de la carte d'un build) et qui ont un `appID` ; `TestFlightCadence` (pur) décide app par app : 15 min au plus tant qu'un build est en traitement, en attente de revue ou en revue, **ou** qu'un build Xcode Cloud vient de finir sans build TestFlight connu de l'heure écoulée (écart au ticket : sans cela un build livré n'est vu que le lendemain), un jour sinon, rien sous `SyncSchedule.criticalRemaining` ; un échec n'est retenté qu'après 15 min, **un 403 est retenu pour la session** (`isForbidden` : la carte dit « Cette clé ne peut pas lire TestFlight. » et plus rien ne part). Sans Pro (`allowed`) ou pour un compte en pause (aucune synchro) : aucune lecture. Chaque lecture garde **l'heure à laquelle Cumulus a vu un état changer** (`TestFlightObservation` : traitement, disponible en interne, disponible en externe), seulement quand la lecture d'avant montrait l'ancien état ; la frise la dit « vu à 14:11 », jamais comme une heure d'Apple. **La frise** : archive réussie (fin de l'action d'archive), envoyé (`uploadedDate`), traitement terminé, revue bêta envoyée (`submittedDate`, absente sans soumission), disponible pour les testeurs ; une étape qu'on ne peut pas dire est omise, un état sans date n'a pas d'heure ; elle n'apparaît que si le store a lu ce build (identifiant commun avec `/v1/ciBuildRuns/{id}/builds`, vérifié) et avec Pro. **Bannières** (`TestFlightAlertPlanner`, pur ; `NotificationCoordinator.testFlightDidRead`) : « <App> 1.4 (412) est disponible pour les testeurs externes » une fois par build, au passage à l'état en test chez les externes, et « <App> : le dernier build TestFlight expire dans n jours » une fois par build à sept jours, pour le build le plus récent en test chez les externes (un build plus récent en test les couvre ; une app qui n'a que des testeurs internes n'a pas cette bannière). La mémoire est par compte (`account.<id>.notifications.testFlight.alertState`, dans `AccountDefaults.names`) ; **la première lecture d'une app dans une session n'envoie rien** et note les builds déjà en test, mais **n'enregistre pas** une expiration proche (elle parle à la lecture suivante, pour qu'un Mac redémarré dans la semaine soit prévenu). Réglages › Notifications, groupe « TestFlight » : deux réglages actifs par défaut (`BuildNotificationRules.testFlightAvailable`, `testFlightExpiry`), grisés sans Pro avec la raison ; un réglage coupé ou une app muette taisent la bannière, pas la mémoire. Le clic ouvre `cumulus://app/<productID>` (adresse ajoutée, `CumulusURL.Destination.app`, lecture seule : la vue d'ensemble de l'app, dans le compte qui la détient). Sans Pro : `ProLockedCard` à la place de la carte (la vue d'ensemble d'une app est déjà une page verrouillée sans `appOverview`), pas de frise, aucune lecture ni bannière. Squelette pendant la première lecture seulement (`SkeletonRules.testFlightBuilds`) ; une lecture qui finit à vide ou en échec ne laisse pas de carte. Hors périmètre : widgets, commande `cumulus`, revue de l'App Store, ajout d'un build à un groupe, envoi vers un webhook. Écart : la carte TestFlight gratuite d'un build lit toujours `ciBuildRuns/{id}/builds` (elle pourrait recevoir `expirationDate` sans requête de plus ; non fait pour ne pas la changer).

**Ce qui a ralenti** (XCO-163, Pro, 14/10/2026) : la section Tendances d'un workflow dit depuis quel build il a ralenti et quelle action en est la cause. `WorkflowSlowdown` (`CLI/`, pur, Foundation seule, non exposé dans `CLIModels` ni dans `cumulus`) cherche dans les 30 derniers builds `SUCCEEDED` (échecs, annulations et builds en cours ignorés) la coupure qui sépare le mieux deux paliers de durée : cinq builds au moins de chaque côté, médiane d'après supérieure d'au moins 15 % **et** 60 s, et la même condition sur les cinq builds juste avant et juste après la coupure (c'est ce qui écarte une dérive lente et régulière, testée). Le build de rupture doit déjà être sur le palier d'après, celui d'avant sur l'ancien (sinon un palier de trois builds se verrait à un build près), et parmi les coupures qui tiennent on garde la plus petite somme d'écarts absolus à la médiane de chaque côté. Seul un ralentissement est trouvé : un workflow qui accélère ne montre rien. La répartition compare, pour chaque nom d'action présent des deux côtés, sa durée médiane avant et après (durées des actions de même nom additionnées dans un build) : celle dont l'écart est le plus grand vient en tête, et n'est nommée comme cause qu'à partir de 15 s. **Limite connue** : une seule rupture par workflow, la meilleure ; si deux ralentissements tiennent dans les 30 builds, c'est le plus net qui est montré. `WorkflowSlowdownModel` (`Window/Workflows/`) y ajoute le build, son SHA court (8 caractères, ceux de `CISourceCommit.shortSha`), la première ligne de son commit, le lien (seulement `https://github.com/<owner>/<repo>/commit/<sha>`, `WorkflowSlowdown.gitHubCommitURL`, plus strict que « Ce qui a cassé ») et le surcoût : médiane après moins médiane avant des coûts de build de `UsageCalculator.cost(of:in:ledger:ratios:productNames:now:)` (les ratios appris une seule fois ; un coût nul, build sans action mesurable, est un trou et non un build bon marché), au moins trois builds chiffrés de chaque côté, au moins 1 min, multiplié par les builds terminés du workflow nés dans le cycle depuis la rupture. Sans forfait, pendant la mesure ou sans calcul possible, la ligne « ~5 min de plus par build, soit ~1 h 10 sur ce cycle. Estimation. » est omise. La carte (en tête de la section, avec le repère en tirets de la rupture sur l'histogramme, nommé à gauche ou à droite selon la place) est sous `ProFeature.workflowTrends` ; « Ouvrir #n » sélectionne le build, « Voir le commit » n'existe que pour une adresse GitHub connue. Aucune requête : tout vient de l'instantané, de l'export d'usage et du forfait, recalculé quand la fenêtre se redessine. **Bannière** : `SlowdownAlertPlanner` (`Notifications/`) lit l'instantané après chaque synchro réussie ; `NotificationCoordinator` ne la cherche pas sans Pro (`ProFeature.slowdownAlert`, comme le build bloqué : rien n'est cherché ni mémorisé) et la mémoire est par compte, workflow par workflow, le build de rupture déjà dit (`AccountDefaults.reportedSlowdowns`, JSON `[workflowID: runID]`, retirée avec le compte). La première synchro d'un compte dans la session mémorise les ruptures déjà là sans rien dire ; une rupture plus ancienne que celle déjà dite est le même ralentissement retrouvé avec plus de builds, une plus récente en est un autre. Le réglage Réglages › Notifications › « Quand un workflow ralentit » (`BuildNotificationRules.slowdown`, actif par défaut) et les apps muettes ne taisent que la bannière, pas la mémoire ; sans Pro la section est grisée avec « Cette alerte vient avec Cumulus Pro. Votre réglage est conservé. ». Titre « <App> · <Workflow> a ralenti de 38 % », corps « Depuis #398, le 7 octobre : Test – iOS est passé de 6 à 11 min. » (ou la médiane du workflow sans action nette), le clic ouvre `cumulus://build/<id>` du build de rupture.

**Branches et pull requests** (XCO-86) : l'entrée « Branches et pull requests » de la barre latérale (`SidebarSelection.references`, adresse `cumulus://references`) remplace la colonne des builds par `ReferencesListView` : une ligne par référence que les builds du cache nomment, avec son dernier build (`ReferencesModel`, pur ; le build d'une PR compte pour la PR, jamais pour sa branche). **Une référence appartient à son app** (XCO-112, choix de l'utilisateur le 12/10/2026) : son identité est `AppReference` (produit + `ReferenceKey`), deux apps qui construisent « main » ont chacune leur ligne, et la liste ouverte ne contient que les builds de cette app. Un clic pose `NavigationModel.referenceScope` et la colonne redevient la liste des builds, limitée à cette référence (`BuildListScope.reference`), avec un retour en tête. Une PR fermée reste dans le cache : `ReferencesStore` lit la liste des PR ouvertes du dépôt (`GET /v1/scmRepositories/{id}/pullRequests`) à l'ouverture de la vue puis toutes les 5 min au plus, pas sous `SyncSchedule.criticalRemaining` ; tant qu'elle n'a pas pu être lue, toutes les PR du cache s'affichent et la vue le dit. **Première récupération** (XCO-83) : `WindowContentState` décide de ce que la fenêtre montre avant d'avoir des colonnes à remplir. **Squelettes de chargement** (XCO-159) : une section qui n'existe qu'une fois ses données lues tient sa place en **squelette** : sa forme finale en gris qui respire, au lieu de rien ni d'une roue. `.skeleton(_ isLoading:label:)` (`Window/Components/Skeleton.swift`) applique `.redacted(reason: .placeholder)`, une opacité de 1 à 0,4 et retour (1,6 s, `withAnimation(.repeatForever)` lancée par un `onChange(of: isLoading, initial: true)` : aucune fermeture d'animation ne lit le `MainActor`, donc pas le piège de `TimelineView`, qui reste interdit), fixe avec « Réduire les animations », coupe les clics et n'expose à VoiceOver qu'un élément « Chargement » (ou le `label` donné) ; hors chargement il ne change rien, et **la vue reste la même vue** : la section réelle nourrie d'un exemple de longueur typique (`static let placeholder` du modèle ou de l'enregistrement : `FailureInsightRecord`, `TestRow`, `IssueGroup`, `CIArtifact`, `WorkflowRow`, `Cycle`, `TestHealthReport`, `ProOffer`…), jamais une copie dessinée à part, donc ni identité qui change (les groupes des fiches restent des enfants directs du `Layout`) ni saut de hauteur. B, le contenu remplace le squelette sur place. **Un squelette n'ajoute aucune requête ni aucune lecture** : il habille l'attente des lectures qui existent déjà. Où : carte « En bref » et carte TestFlight d'un build (seulement un build réussi d'un workflow qui livre à TestFlight), parties Tests (une action de test terminée), Problèmes et Artefacts de la fiche d'un build (barre de progression gardée au-dessus), Vue d'ensemble pendant la mesure, carte du cycle et pastille TestFlight de la vue d'une app, faits, description et conditions de démarrage d'un workflow tant que sa fiche n'est pas lue, section Tests d'un workflow, popover de l'histoire d'un test, carte du cycle de la barre latérale, sélecteur de source de la feuille de lancement, offres de la feuille d'achat (les deux cartes, le bouton et les mentions, même hauteur avant et après les prix ; l'état `.unavailable` reste un message), menus de versions de la feuille de modification d'un workflow, état et boutons du volet Cumulus Pro tant que `ProStore.hasResolved` est faux.

**Localisation** (XCO-21 à 23) : langue source anglaise, `Localizable.xcstrings` traduit en français. `xcodebuild` ne met pas à jour le catalogue source (seul Xcode le fait) : après l'ajout d'une chaîne, le resynchroniser avec `xcrun xcstringstool sync xcode-cloud-companion/Localizable.xcstrings --stringsdata <DerivedData>/…/Objects-normal/arm64/*.stringsdata`, puis traduire la nouvelle entrée (le test `FrenchLocalizationTests` échoue sinon). ## 2. Workflow

### Branches

Le travail se fait sur une **branche de feature** au format `claude/<description>-<hash>` (ou `codex/…` pour Codex), créée **dans le dossier principal** du dépôt, pas dans un `git worktree`. **Ne jamais commiter directement sur `main`**, ne pas pousser la branche vers `origin` ni ouvrir de PR de soi-même : le travail reste **local** pendant tout le statut **In Review**, pour que l'utilisateur le teste sur sa machine.

Un ticket demandé en cours de session se développe **sur la branche en cours**, avec son propre commit. Ne changer de branche que si l'utilisateur le demande.

Une fois l'utilisateur revenu avec sa validation (ticket → **Done**, cf. § Tickets) : squash-merge de la branche dans `main` en local, puis suppression de la branche.

```bash
git checkout main
git merge --squash claude/<branche>
git commit -m "XCO-12: …"          # ou « projet: <nom du projet> », cf. § Style de commits
git branch -D claude/<branche>     # -D : après un squash, git ne voit pas la branche comme fusionnée
```

Plusieurs sessions peuvent tourner en parallèle dans ce dossier :
- toujours stager des **chemins explicites** (`git add <chemins>`), jamais `git add -A`, `git add .` ni `git commit -a` ;
- `git status --short` et `git branch --show-current` juste avant chaque commit ;
- jamais de `git reset --hard`, `git stash` ni `git checkout -- .` global.

Les reformatages massifs faits par Xcode (imports, accolades) se laissent tels quels.

### Style de commits

Titres courts **en français, à l'indicatif, qui disent l'effet produit** plutôt que le fichier touché (« Le menu montre les heures consommées sur le cycle », « Un build échoué s'affiche en rouge dans le sous-menu de son app »). Préfixe :

- **un ticket** : son identifiant, sans type ni parenthèses — `XCO-12: Le menu montre les heures consommées sur le cycle`. Plusieurs tickets dans un même commit : le préfixe une seule fois, puis les numéros séparés par des tirets — `XCO-3-4: …` (chaque numéro est cité, ce n'est pas un intervalle) ;
- **un projet Linear entier, squash-mergé d'un coup** : `projet: <nom du projet>`. Le corps du commit liste alors les tickets, un par ligne (`XCO-12 Le menu montre les heures consommées sur le cycle`), puisque le squash efface les commits par ticket ;
- **aucun ticket** (retouche d'AGENTS.md, rapports) : le titre seul, sans préfixe.

### Granularité des commits

Sur une branche qui traite plusieurs tickets, faire **un commit distinct par ticket** dès que son implémentation est cohérente (tests ciblés inclus). Ne pas accumuler les changements jusqu'à la fin du lot, et ne pas mélanger les fichiers de tickets indépendants dans un même commit. Si un fichier partagé est modifié par plusieurs tickets, séparer ses hunks dans l'index.

## 3. Conventions de code

- **Concurrence Swift 6 stricte, isolation par défaut `MainActor`** (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, `SWIFT_APPROACHABLE_CONCURRENCY = YES`). Chaque type reçoit une isolation choisie, pas subie :
  - **`MainActor` seulement pour ce qui touche l'interface** : vues SwiftUI, `NSStatusItem` / `NSMenu`, état observé par les vues ;
  - **`nonisolated` pour tout le reste** : modèles de données (structs `Sendable`), décodage, calcul de l'usage, construction des requêtes, formatage. C'est le cas le plus fréquent ;
  - **un `actor` seulement s'il protège un état mutable partagé** (cache, jeton JWT en cours de validité) ;
  - **de l'asynchrone seulement quand c'est indispensable** (réseau, disque, trousseau). Une fonction de calcul reste synchrone ;
  - **pas de saut d'acteur inutile** : on ne fait pas d'aller-retour vers le `MainActor` pour une donnée qui peut se calculer ailleurs, et on ne passe à l'interface que le résultat final.
- **Économie de données** : ne demander à l'API que ce qui sert (`fields[…]`, `limit`, `include` ciblés), ne pas redemander ce qui est en cache, ne garder en mémoire que ce que l'interface affiche.
- **Pas de contournement** : ni `nonisolated(unsafe)`, ni `@unchecked Sendable`, ni `@preconcurrency import`. Chercher la vraie isolation ; si un contournement semble inévitable, le signaler et le justifier.
- **Ajout de fichiers** : le projet utilise des groupes synchronisés, un fichier créé dans `xcode-cloud-companion/` est pris en compte sans éditer `project.pbxproj`. Un fichier créé dans `CLI/` entre dans l'app et dans la commande `cumulus`.
- **Secrets** : la clé `.p8`, l'Issuer ID et le Key ID vivent dans le trousseau. Ne jamais les écrire dans le code, les logs, les tests ni les tickets.
- **Tests** : Swift Testing. Le calcul de l'usage (cycles, quota, rythme) et le décodage des réponses de l'API se testent avec des fixtures JSON, sans appel réseau.
- **Commentaires** : aucun par défaut. Seulement pour un *why* non évident (contrainte de l'API, invariant caché).
- **Pas d'emoji dans les fichiers source**, sauf demande explicite.
